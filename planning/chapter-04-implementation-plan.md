# 第四章实施计划

日期：2026-11-11。适用章节：CH-TOOL，第 4 章《第一个业务工具：让查询函数进入一次任务》。编写依据为 V6、总体实施安排及第四章评审。本文件只细化第四章，不增加总体方案版本，不表示以下工作已经实施。

## 1. 完成目标和当前起点

读完本章，学生应能把第三章的普通查询函数通过插件接入 goodtang/deepseek-harness-local，自己增加一项只读工具，并用实际调用、结果和失败对照验证它。能运行教材命令不等于能开发工具；能背出 inject/apply/register 也不等于理解它们。

当前基线为书稿提交 `09e5618ee0c38530a49b3eafdea299e14c944682`。4.1–4.3 已写，真实正常路径证据为 `labs/first-tool/evidence/normal-ch04-start.json`；4.4–4.5 尚未交付。写作状态保持“正式初稿中”，技术、图稿及连贯性部分通过，读者未检查。上游研究基线 `fcc0ad462172522aaf5c93a7b2e01f6b9f0b0159`，开始运行前重核 HEAD 和跟踪文件状态。

现有证据可证明正常工具循环、实际 stdout 和清理；不能证明错误参数在业务执行前被拒绝，也不能证明库存迁移可行。当前不足还包括亲手编写步骤、必要知识的分步教学和原始记录的阅读示范。

## 2. 章内学习顺序

| 小节 | 学生遇到的问题 | 必须交付的学习成果 |
| --- | --- | --- |
| 4.1 从函数走到插件 | 函数能运行，为何还不在工具列表里 | 区分业务函数、工具定义、插件；解释两版函数差异 |

## 3. 实施约束与文件职责

- 始终通过受支持的 dsh profile 启动，工具经过实际注册和执行管线；不以直接调用 execute 充当集成实测。
- 固定工单 `TK-1042`、工具名 `book_ticket_lookup`、函数 `lookupTicket(id)` 及三个字段。用插件扩展能力，不改上游 agent-loop。
- 读者使用实际 BookRoot/HarnessRoot，不预设盘符、相邻目录或作者布局。区分准备好的加载设施与学生亲手编写的业务代码。
- 只读虚构业务；不用真实模型 key。模拟、真实 Harness 执行、真实模型选择能力分别表述，不把本机 mock 当已验证断网。
- 不重写已有插件/函数/运行器以迁就新实验，避免使前三章及旧证据失效。新增设施优先放在 `labs/tool-cases/`；确有共享修改需要时同步核对全部消费者和证据版本。
- 每轮只完成 1–3 个相邻小节或一个可验收实验，范围服从章内连贯性和上下文容量。每轮至少留出检查、提交和接续的空间。

## 6. 工作包 C：完成 4.4 的三个对照实验

先建立最小场景运行入口，再逐个场景实施、留档和写解释。计划入口语法为：

```powershell
$CaseEvidence = Join-Path $BookRoot 'labs/tool-cases/.lab-runtime/normal-01'
Set-Location -LiteralPath $HarnessRoot
node --import tsx/esm (Join-Path $BookRoot 'labs/tool-cases/run.mjs') $HarnessRoot normal $CaseEvidence
```

以上为新增运行器实现后的命令设计，目前不应执行。CaseEvidence 必须指向尚不存在的目录，已有 normal-01 时更换末段编号，不能覆盖旧记录。场景名固定为 `normal`、`missing`、`invalid-argument`、`unregistered`，库存集成使用 `inventory-zero` 和 `inventory-missing`。运行器只在其证据断言及清理均通过时退出 0；应用自己的退出码另存，不能预先假定业务错误时应用一定非零。

- [ ] C1 先以 normal 验证新的执行记录设施：工具存在、结果正确、execute 进入次数为 1。执行记录在业务函数调用前写入隔离实验记录，只服务教学测量，不加入上游产品日志或模型可见输入。
- [ ] C2 设计错误注入验证执行记录可信：若记录丢失，normal 必须失败，不能将“没有文件”默认为 execute 从未执行。记录格式、作用路径和采集方法写入 README。
- [ ] C3 场景 missing：工具存在，输入 `{"id":"missing"}`，execute 进入一次，实际成功结果为 null，并进入后续请求。它是正常业务缺失，不应当作执行错误。
- [ ] C4 场景 invalid-argument：工具存在，输入 `{"id":1042}`。要求捕获真实参数拒绝结果、调用关联和 execute 进入次数为 0；先定位实际错误字段和措辞，再写正文。只看到错误文字不足以通过。
- [ ] C5 场景 unregistered：保留同一业务函数与其他准备，只取消插件的工具注册，检查首次工具列表没有 book_ticket_lookup。若模拟服务继续发出该调用，还须记录真实未知工具处理结果；不凭猜测规定其错误措辞。
- [ ] C6 每做完一个场景，就回写 4.4 对应段落和预测表，再运行受影响的正常路径回归。错误实验后说明怎样恢复有效版本。

| 场景 | 工具定义 | 输入 | 业务 execute 进入次数 | 结果核查 |
| --- | --- | --- | --- | --- |
| normal | 有 | 字符串 TK-1042 | 1 | 已知工单对象，关联到原调用 |
| missing | 有 | 字符串 missing | 1 | 非错误的 null，进入后续请求 |
| invalid-argument | 有 | 数字 1042 | 0 | 参数被拒绝，关联证据齐全 |
| unregistered | 无 | 同一工具名的模拟调用或工具列表观察 | 0 | 定义确实缺失；调用时记录实际未知工具结果 |

以上是待验证的验收预期，不是已有结果。若实测与预期不同，保存失败原件，检查源码及配置后修正设计或发现的问题；不能修改断言把异常包装为通过。每个场景保存工具/调用/结果、应用及运行器退出码、输入、执行记录、实际 stdout/stderr、文件哈希、源码版本、服务/子进程/临时目录清理。

完成条件：三个对照及 normal 正对照分别实跑通过，能在正文解释“业务不存在、参数无效、工具未提供”的区别；旧正常案例回归通过。查不到的本地函数断言不能替代本包集成实验。

## 7. 工作包 D：完成 4.5 的库存迁移

固定独立练习：函数 `lookupInventory(sku)`，工具 `book_inventory_lookup`，参数为必填字符串 sku。虚构商品 `SKU-1001` 返回 `{ sku: 'SKU-1001', name: 'Notebook', stock: 0 }`，不存在的 `SKU-missing` 返回 null。输出声明允许对象或 null，stock 为数值。库存 0 是有效记录，不能用 stock 是否为真判断商品是否存在。

- [ ] D1 先实现作者参考函数与插件，建立本地断言：完整对象、0 库存、缺失商品、修改返回副本不影响原记录。
- [ ] D2 用真实 profile 分别验证 inventory-zero 和 inventory-missing；核对工具定义、参数及结构化结果、render 内容和后续请求，正常工单工具另作回归。
- [ ] D3 给学生一份可运行起点和明确完成清单，只给方法提示，不直接把完整参考答案放在练习之前。分别记录独立完成、借助提示和未完成，不由作者代填。
- [ ] D4 让学生自己增加一个非零库存商品，并同时回归零库存、缺失商品和旧工单；作者参考解先证明这组任务可行。
- [ ] D5 章末要求学生画出或说明“自己的业务函数 → 插件工具定义 → tools 服务 → 实际调用/结果”的关系，给第五章留下真实结果和待追问的消息组装问题。

本地计划命令：`node labs/tool-cases/check-inventory.mjs`。在实现后的正例通过后，故意把“存在性判断”改成 stock 是否为真，0 库存检查必须失败，再恢复正确版本；这项错误注入用于验证断言有效。

完成条件：本地与真实集成各自有实际记录；参考解能完成练习，学生验收仍独立保留。不以另建一套模拟工具循环代替对目标 Harness 的迁移开发。
