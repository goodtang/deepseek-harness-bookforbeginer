# DeepSeek Harness 教学书方案 v2：评审与优化建议

日期：2026-11-10。

评审对象：[DeepSeek 方案 v2](deepseek-harness-book-plan-v2.md)，并对照[原规划稿](deepseek-harness-book-plan.md)。本次评审只针对教材方案；没有修改两份原稿，也没有执行其中的业务开发或发布建议。

## 摘要

建议以 v2 作为下一版基础，保留十篇骨架、主线案例、递进实验、自动生成模块清单和先交付样章的做法。优先修正预算与事实表述，再补齐零基础学习依赖、实验验收与业务项目定义。

目前最主要的问题是：目录比教学验证走得更快。52 章已经排定，但基础知识怎样过关、模块怎样算覆盖、实验怎样证明业务能力，尚缺少足够具体的约定。下一版应先补这些内容，再扩写正文。

## 一、建议保留的内容

1. 保留“机制讲解、源码追踪、开发查阅、业务迁移”四项目标，比单纯按目录讲包更接近读者需要。
2. 保留十篇骨架与数据设计独立成篇的安排，但允许样章验证后调整章节数量和顺序。
3. 保留一条贯穿主线和两个迁移案例，让读者在同一业务背景中不断增加能力。
4. 保留模块覆盖表，并由机器生成能够可靠提取的字段，人工审核职责、讲解与证据。
5. 保留模拟模型与录制回放，分别用于故障控制和已录制场景复现。
6. 保留“目录、覆盖表、两章样章”作为第一批成果，先验证教学质量再批量写作。

v2 在具体化方面有帮助，但其中部分安排是对原规划的细化，例如“一主线加两迁移案例”和“四级覆盖”。它们无需继续作为两个方案的分歧保留。正式编写计划建议删除“与 Codex 规划稿的关系”，直接陈述最终方案。

## 二、优先修正的问题

### 2.1 字数预算存在算术冲突

十篇分别为 5、7、6、12、10、10、6、6、8、9 万字，合计为 **79 万字，尚未计入附录**，与正文多处承诺的“65–70 万字”不一致。

篇四与篇五合计 22 万字，占十篇预算约 27.8%，也不符合“约 35%”的说法。核心精读清单所列行数相加为 42,365 行，与“约 4.2 万行”相符；本次只复核其加总，没有重新测量每包源码行数。

建议先确定各篇的必达成果，标记必读、进阶和查阅内容，再估算篇幅。字数作为预算，源码行数作为研究量参考，两者不能直接决定章节篇幅。精简版需要单独列出保留章节与实验，不能只把完整版压缩到 25 万字。

### 2.2 “100% 覆盖”缺少明确分母

“机制与扩展点 100% 覆盖”只有在机制与扩展点清单明确后才可验收。当前表格主要按包组织；包、机制、扩展点并不一一对应。

建议分别建立模块清单、机制清单与扩展点清单。每项关联所属章节、源码依据、消费者、配套实验、验证状态和未完成范围。覆盖率分开统计“已定位、已讲解、已实践、已验证”，不把模块索引中的一行视为完整讲解。

实验性模块可以只做定位与分类，但需要说明哪些只提供地图、哪些深入讲解。任何排除项都写进范围清单，避免“所有代码”与“不覆盖全部 experimental”产生不同理解。

### 2.3 无真实密钥、离线与确定性需要分开承诺

v2 将三者合并为一条要求，但模拟模型只能消除真实模型调用这一类依赖。包安装、浏览器下载、外部 MCP、业务服务和桌面构建仍可能需要网络或平台工具；并发请求、端口、文件路径、时钟和调度也可能影响结果。

建议改为：“基础运行时实验不依赖真实模型凭据；完成环境准备后，明确列出的核心实验能够在阻断外网时运行；实验对可观察结果提供明确且可重复验证的断言。”占位凭据应明确称为测试凭据。

模拟服务的脚本按请求到达顺序消费。并发会话共用一个游标时，即使固定随机种子，也不能据此保证故障分配给固定会话。相关实验需要独立实例或受控请求顺序，参见[模拟服务限制](https://github.com/goodtang/deepseek-harness-local/blob/fcc0ad462172522aaf5c93a7b2e01f6b9f0b0159/packages/test-support/llm-mock-server/README.md#known-limitations-and-deferred-work)。

### 2.4 “日志是唯一事实”表述过宽

设计主题 T3 写成“日志是唯一事实”，容易让初学者误以为文件、外部业务系统、凭据和运行时资源都以 Session 日志为唯一依据。架构文档强调的是模型可见内容需要能够从会话记录重建。

建议改为：“模型请求的相关输入应可从 Session 记录及其解释规则重建；业务数据库、文件与外部系统各有自己的权威数据来源。工具日志记录执行情况，不自动证明外部副作用已经成功。”

这一点也需要落实到实验：业务写操作执行后应重新读取外部状态验证，不能只检查 Agent 的答复文本。参见[测试原则](https://github.com/goodtang/deepseek-harness-local/blob/fcc0ad462172522aaf5c93a7b2e01f6b9f0b0159/docs/testing.md#verify-the-world-not-the-self-report)。

### 2.5 “已核实”需要附带复现证据

v2 标注 mock 与回放“已验证可用”，但没有附测试环境、具体命令、输出、退出状态与清理记录。设施存在、帮助命令可运行、完整应用接入成功、教材实验稳定通过，是不同的验证层次。

建议增加验证记录表：基线提交、平台、依赖准备、命令或实验 ID、断言、结果、记录文件、验证时间和未覆盖范围。保留已有验证结论时，应链接其原始证据；本次没有重跑它们，不能替已有记录背书。

## 三、教学与源码研究的优化

### 3.1 把“必备基础”拆成可过关的基础单元

第 1.4 章同时承担 TS、ESM、异步、取消、工作区与测试，对真正零基础读者跨度过大。仅完成一个带取消的小练习，难以证明已经具备阅读真实框架的基础。

建议保留开篇黑盒体验，然后提供可独立学习的小单元：变量与函数、对象与数组、类型与联合类型、模块导入导出、Promise 与 async/await、错误传播与取消、测试与调试。每个单元给出练习及进入后续章节所需的最低成果。

基础内容可以放在入门分册或附录，并在正文按需引入。篇四可以依赖“已完成异步与取消练习”，不能只依赖“已读第 1.4 章”。阅读计划应先统计每周可投入时间，再根据试读结果估算，暂时撤下“每周三章”的统一节奏。

### 3.2 调整循环与数据的学习依赖

篇四已经讨论记录、请求历史和恢复，但完整 Session 数据设计在篇五才出现。可以在篇四开头增加最小 Session 导读，只介绍事件、消息、序号与请求重建需要的知识；篇五再深入持久化、投影、迁移与数据归属。

也可以拆为“会话基础 → 执行循环 → 数据进阶”。最终顺序通过样章试读决定，不必为了维持 52 章而保留知识跳跃。

### 3.3 核心精读按流程选择，不以十个包封顶

十个包可以作为研究起点，但关键行为可能分散在重试、上下文、投影、作用域、子 Agent 激活和客户端同步等实现中。只精读所列包，可能把最重要的生命周期与状态协调留在范围之外。

建议让关键流程决定精读集合。每条流程至少覆盖入口、类型、实现、实际消费者、持久记录和验证。其余模块按家族解释，再通过覆盖表检查没有遗漏的机制。

### 3.4 自动生成清单与人工研究分工要统一

文档分别写了“只填深度与证据”“只填后四列”“只填三列”，需要统一。`package.json` 与模块依赖图可以提供包与依赖信息，不能直接可靠推导全部业务职责、动态消费者、事件语义和教学深度。

建议由脚本提取路径、包名、依赖和已有文档链接；利用 CodeGraph 提供符号与结构关系；由作者审核职责、消费者解释、章节映射与验证证据。自动提取字段与人工判断字段分别标记。

### 3.5 源码坐标要有固定写法

当前混合了完整路径、包分组简称、文档和命令。`core/agent-loop` 可以作为展示简称，但自动校验需要同时保存完整仓库相对路径和符号名称。

例如，基线工作树中不存在根目录 `profiles/`，也不存在 `packages/session/persistence`。前者需要区分代码位置与 Harness home 中运行时生成的 profile 数据；后者应在研究后指向实际持久化实现。命令应放入运行方式字段，不能当作源码路径。

### 3.6 增加从原理到独立实现的明确章节

“构建教学用最小 Harness”已列为第 12 级实验，但 52 章中尚未明确谁负责讲解。它直接关系到用户“能开发自己的 Harness”的目标，需要指定章节、实现范围和验收条件。

建议至少比较输入队列、模型请求、工具执行、事件记录、取消、状态显示这几项。每完成一项，说明教学简化与正式仓库的区别，再解释加入业务权限、恢复和并发后需要哪些工程机制。独立教学实现与正式 `dsh` 应用扩展应明确分开。

## 四、实验与业务项目的优化

### 4.1 每个实验需要结构化说明

| 字段 | 内容 |
| --- | --- |
| 标识与目标 | 实验 ID、前置知识、学完能够完成的操作 |
| 运行条件 | 基线提交、平台、运行时、准备阶段网络需求与测试凭据 |
| 隔离 | 临时 Harness home、工作目录、端口与环境变量 |
| 操作 | 输入、步骤、启动方式与所需配置 |
| 验证 | 外部状态、会话记录、请求内容或界面结果的具体断言 |
| 故障 | 至少一个与本章相关的失败或取消场景 |
| 清理 | 子进程、监听端口、文件和服务如何释放 |
| 证据 | 验证结果与对应记录位置 |

“观察卸载残留”应变为验证监听器、注册项或子进程是否释放；“验证恢复”应明确是请求重试、会话重新附着、进程重启还是业务补偿。这些行为不能合并为一个笼统的恢复成功。

### 4.2 区分模拟故障、会话回放与真实集成

模拟模型适合精确安排响应、工具调用和协议故障；会话回放适合复现已录制场景并检查记录与显示；真实集成用于验证当前模型或外部业务服务。三者的证据不能互相替代。

建议 CI 默认运行重点基础实验；真实集成按凭据和平台单独执行。桌面构建、签名、原生能力、SSH 与外部业务服务的实验标记平台条件，避免将整书所有实验都归为离线核心实验。

### 4.3 将三个综合项目定义出来

v2 宣布三个 capstone，但没有完整说明各自输入、输出与验收。建议明确为以下递进项目，复用同一业务背景：

| 综合项目 | 交付成果 | 关键验收 |
| --- | --- | --- |
| 核心任务处理 | 只读问题处理助手、教学最小循环与正式实现对照 | 能追踪模型与工具执行，取消后能说明状态与记录 |
| 可控业务执行 | 接入本地模拟业务服务，增加确认、写操作与协作 | 外部状态可核查，重复请求和未知结果有处理方式 |
| 可交付应用 | SDK 或 Web 入口、业务卡片、持久记录与运行说明 | 能在干净环境运行，完成故障恢复与维护演示 |

“设计一次不可逆操作”建议先在可重置的本地业务服务中练习，验证确认、幂等、结果核查和审计。是否连接真实业务环境属于另行定义的集成阶段。

### 4.4 教学项目也要体现业务架构

增加“模型层、Harness 执行、确定性业务服务、权威数据源、人工作业”之间的职责图。让读者回答哪些步骤允许模型判断，哪些规则必须由业务代码检查，谁决定权限，谁保存最终业务状态。

这样能把实现扩展能力与实际业务开发能力联系起来，也能防止读者把工具返回成功或模型自述误认为业务已完成。

## 五、下一版的具体改法

建议对 v2 做定向修订，暂不重写全部内容：

1. 将 52 章标为候选目录，允许根据学习依赖和试读拆分合并。
2. 统一字数总账，给精简版单独列出必读章节、实验和排除项；排期在两章样章后重估。
3. 增加入门基础单元、学习依赖图和最小 Session 导读。
4. 增加模块、机制与扩展点三类清单，统一自动生成与人工审核字段。
5. 将实验要求改为“无真实模型凭据、明确离线范围、断言可重复”，补实验说明与验证记录。
6. 修正“日志是唯一事实”“读者改代码即生效”等过宽表述。`start:web` 与 `dev:web` 的构建和更新行为需要分开说明，不能互换。
7. 给教学最小 Harness 与三个综合项目分配明确章节、输入输出和验收要求。
8. 删除两个 AI 方案之间的比较章节，让正式方案只保留最终教学安排；需要保留的讨论放到规划历史中。

第一批交付仍建议限定为目录、覆盖表与两章样章，但每个样章必须带可运行实验及验证证据。外加一名初学者的试读记录，记录卡住的位置、补充解释次数与独立完成情况。没有实际试读时，应标为“作者自测通过，读者验收待完成”。

- 复算十篇字数、核心清单行数总和及篇四、篇五占比；未重新统计全仓库包数或行数。

- 执行 `corepack pnpm run mock:llm --help`，退出码为 0；这只确认帮助命令可运行，没有证明完整 profile 实验通过。
- 没有运行完整快照测试、Web 测试、真实模型或业务集成，没有验证 v2 所述全部实验。

本评审不重复确认 v2 的所有“实测”指标。下一版应为这些指标附统计口径、基线和原始报告，作为可维护的研究记录。
