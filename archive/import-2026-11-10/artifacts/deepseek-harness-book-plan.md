## 摘要

本项目计划以 DeepSeek Harness 仓库为真实教材，编写一本中文教学书，让零基础读者从必备编程知识开始，逐步掌握底层框架、Agent 控制、数据设计、能力扩展、服务协议、客户端交互与工程交付，并能够基于项目完成实际业务的二次开发。

这本书同时承担顺序学习、源码研究与开发查阅三个任务。教学主线负责循序渐进，源码详解负责解释实现，业务实战负责能力迁移，模块索引负责追踪全仓库覆盖。

## 一、需求理解与最终目标

### 1.1 要解决的问题

读者需要知道一个功能解决什么问题、为何采用当前设计、代码如何配合、数据如何流动、失败如何处理，以及业务需求应该从哪里扩展。全书需要把设计、框架、模块、实现和实践联系起来，避免出现读懂局部函数却无法理解完整任务的情况。

最终学习成果是能够独立解释系统、追踪源码、修改实现、扩展业务并验证交付。对于希望构建自己的 Harness 的读者，书中还应提供教学用最小实现，再把它与正式仓库的工程实现逐项对照。

### 1.2 将“完全掌握”变成可检验的能力

| 能力 | 读者需要做到的事情 | 建议验收方式 |
| --- | --- | --- |
| 理解原理 | 解释模型、Agent、工具、循环、上下文和状态的关系 | 用自己的语言说明一个任务为什么需要多次模型请求 |
| 看懂架构 | 说明模块职责、依赖方向与扩展位置 | 为一个业务需求画出涉及模块与调用顺序 |
| 阅读源码 | 从用户入口追踪到请求、工具、事件、存储与显示 | 标出关键入口、类型、实现与测试 |
| 修改实现 | 判断变更影响哪些消费者、协议、数据与文档 | 完成一个有明确影响范围的修改 |
| 扩展业务 | 增加工具、插件、适配器、流程或界面 | 在支持的应用启动方式下运行扩展功能 |
| 独立构建 | 根据原理构建教学用最小 Harness | 演示输入、模型调用、工具执行、记录与输出 |
| 验证与交付 | 处理取消、失败、权限、恢复、测试与升级 | 通过业务验收与故障场景验证 |

### 1.3 “所有代码”的覆盖约定

所有模块都需要有可检索的定位、职责、依赖、使用场景和源码入口。核心机制需要深入到关键类型、状态变化、算法、生命周期和失败路径；相似实现需要解释共性及有意义的差异。

覆盖还应包含应用入口、Python SDK、原生能力、构建脚本和测试基础设施。对第三方与 vendored 实现，需要说明其作用、使用方式和项目依赖的行为；对实验性模块，需要清楚标注其状态。具体精读清单在全仓库盘点后确定。

逐行解释的深度根据机制决定。通过覆盖表记录每个模块被讲解到哪里、哪些细节尚未研究，避免把一个目录链接当作已经完成教学。

## 二、读者起点与学习路线

### 2.1 默认读者

默认读者没有 Agent 框架开发经验，也不预设其已掌握 TypeScript、Node.js、异步编程、插件架构、事件日志或前后端通信。书中应说明每个术语的含义，并在依赖该概念之前提供足够基础。

基础知识按项目需要引入。例如，在工具执行之前介绍 Promise、错误传播和取消；在事件定义之前介绍联合类型和类型收窄；在插件卸载之前介绍资源归属与释放。必要的补充练习放在对应章节或附录。

### 2.2 主学习路线

学习顺序为：完整体验 → 必备基础 → 底层框架 → 启动组合 → 核心执行与数据 → 能力扩展 → 服务与交互 → 业务开发与交付。

开篇先展示一次完整任务：用户发出请求，系统组织模型输入，模型请求工具，系统执行工具并记录结果，后续请求生成答复，界面显示执行状态与结果。此时只解释各部分的目的，随后再从底层逐层展开实现。

书中的教学分层应与仓库实际依赖关系分开说明。章节先后顺序表达学习依赖；真实模块图表达代码依赖，两者不能混用。

### 2.3 建议阅读路径

| 路径 | 适用读者 | 阅读方式 |
| --- | --- | --- |
| 零基础学习 | 从未开发过相关系统的学生 | 按顺序学习基础、核心机制和实验，再完成业务项目 |
| 有经验的工程师 | 熟悉编程但不熟悉本仓库 | 完成整体导览与核心机制，再按业务需求深入能力和交互 |
| 二次开发查阅 | 已理解核心运行方式的开发者 | 从业务需求进入模块索引，查阅扩展点、数据与验证要求 |

各路径需要共享术语、源码索引和版本基线。学习时间取决于基础与实践投入，在样章和实验试读前不承诺固定掌握周期。

## 三、全书结构建议

暂定书名为《从零理解与开发 DeepSeek Harness：架构、源码与业务实战》。以下为篇级目录，详细章目应在源码覆盖表建立后展开。

### 第一篇：起步与基础

内容包括 Agent 与 Harness 的区别、一次任务的完整旅程、开发环境、Git、TypeScript、Node.js、模块与依赖、异步执行、测试基本概念和仓库阅读方法。

学习成果：能够运行经验证的入门示例，阅读简单模块，解释一个最小插件的作用。

### 第二篇：框架底层

内容包括 Cordis、Context、Plugin、Service、服务依赖、事件模式、effect、注册与释放、插件生命周期，以及配置与重载相关机制。

学习成果：能够编写具有明确依赖与资源释放行为的插件，解释插件之间如何协作，并验证加载失败与卸载行为。

### 第三篇：启动与组合

内容包括 CLI 入口、profile、bundle、配置覆盖与插件树组装、应用启动，以及 Web、无界面运行、SDK 与桌面应用的组合方式。

学习成果：能够解释从启动参数到运行插件树的过程，并通过受支持的 profile 与配置扩展方式组装自己的运行环境。

### 第四篇：Agent 执行

内容包括 Agent 接口、AgentLoop、状态机、turn 与 step、收件箱、输入调度、提示组装、工具选择、模型请求、流式输出、工具执行、继续执行、取消与终止。

学习成果：能够追踪一次任务，解释任务何时继续和停止，定位请求或工具执行问题，并通过相应扩展点调整行为。

### 第五篇：数据设计

内容包括 Session 事件日志、消息与模型历史、状态投影、持久化提供者、恢复、迁移、上下文压缩，以及会话数据、配置、凭据、附件和其他存储之间的责任划分。

学习成果：能够说明一项状态的来源与恢复方式，判断哪些数据需要持久化，设计可恢复的业务记录，并识别数据变更的兼容性影响。

### 第六篇：能力与扩展

内容包括服务定义、提供者与消费者，文件与工作区、进程与 Shell、持久终端、SSH、沙箱与审批、Web、LSP、MCP、技能、交付物、后台任务与调度等能力。

学习成果：能够选择合适的业务扩展位置，接入外部系统，并说明执行环境、权限、超时、取消与失败的处理责任。

### 第七篇：多 Agent 控制

内容包括子 Agent 创建与生命周期、消息与输入、发现、等待、中断、资源与预算控制、团队任务板、工作流以及预设组合。不同机制的关系需要依据源码逐项核实。

学习成果：能够设计任务拆分、协作与结果汇总流程，处理协作者失败、取消、超时和重复工作，并通过记录追踪执行情况。

### 第八篇：服务与协议

内容包括 Host 与 API、BFF、RPC、请求与响应类型、流式同步、连接恢复、TypeScript 与 Python SDK、ACP，以及外部系统驱动任务的方式。

学习成果：能够从业务应用调用 Harness，明确进程与网络通信中的验证责任，并跟踪服务端状态如何传递到调用方。

### 第九篇：客户端与交互

内容包括客户端启动、插件激活、会话状态、流式显示、消息和工具卡片、人工反馈与审批、扩展区域、响应式布局、主题、国际化、键盘与焦点，以及桌面应用集成。

学习成果：能够为业务能力设计完整交互，包括执行中、等待人工操作、取消、失败、恢复与完成，并追踪界面状态与持久记录的关系。

### 第十篇：业务开发与交付

内容包括需求拆解、扩展位置选择、业务数据、外部服务集成、权限与审批、可观测性、测试、性能、部署、排错与升级。业务权限和租户隔离等能力应逐项确认已有支持与待开发范围。

学习成果：能够独立完成一个业务应用，并提供设计说明、实现、验证证据、运行方式与维护说明。

### 附录

附录包括术语表、全仓库模块地图、关键类型与事件索引、数据索引、扩展点索引、源码阅读清单、故障排查、练习答案和版本对照。已有生成型清单优先链接其权威来源，避免维护重复清单。

## 四、每章的教学结构

| 章节环节 | 必须回答的问题 |
| --- | --- |
| 问题与目标 | 解决什么问题？学完能够完成什么操作？ |
| 前置知识 | 依赖哪些概念？尚未掌握时从哪里补学？ |
| 最小例子 | 能否用一个小而完整的例子观察该机制？ |
| 设计与图解 | 谁负责什么？控制、数据与生命周期如何联系？ |
| 真实源码 | 从哪里进入？涉及什么类型、实现、消费者与测试？ |
| 设计取舍 | 当前设计有什么收益、成本与适用条件？证据来自哪里？ |
| 动手实验 | 改动哪些内容？如何运行？预期观察到什么？ |
| 故障与自测 | 怎样制造失败、定位原因、恢复并证明自己理解？ |

正文需要解释关键代码，长代码通过稳定的源码链接和阅读范围承接。首次出现的术语使用中文解释并附原名；同一概念在后续章节保持一致。

例如，“取消任务”需要讲清取消如何进入 Agent，如何传播到模型请求与工具，当前执行如何收敛，结果如何记录，以及界面如何显示。读者应通过实验观察每一环节，而不只学习一个取消 API。

## 五、源码研究与覆盖方法

### 5.1 建立可追踪的覆盖表

每个模块至少记录源码路径、职责、关键入口、核心类型、依赖与消费者、相关事件或存储、所属章节、讲解深度、配套实验、验证证据和待研究问题。

| 覆盖层级 | 研究范围 | 交付要求 |
| --- | --- | --- |
| 全局定位 | 所有模块及主要非包目录 | 能从模块索引找到用途、关系与阅读入口 |
| 核心精读 | 框架、启动、循环、会话、工具、模型与协议等关键机制 | 给出关键实现、时序、状态与失败处理 |
| 能力分类 | 各类能力实现与适配器 | 解释共同接口、消费者与各实现差异 |
| 工程支撑 | 测试、构建、发布、原生与平台相关实现 | 解释运行条件、作用及修改后的验证要求 |

覆盖完成状态应由实际研究与验证记录决定。无法确认的行为列为问题，不以推测填补。

### 5.2 用完整流程串联模块

至少需要研究用户输入、提示与工具组装、模型流式响应、工具执行与结果记录、任务取消、恢复、多 Agent 协作以及客户端更新等流程。

对每条流程，分别检查控制流、数据流与资源生命周期。展示调用顺序的同时，解释哪些内容会持久化、谁负责释放资源，以及失败后哪些操作可以安全重试。

### 5.3 区分事实、记录与分析

源码与测试用于确认当前行为；维护中的文档用于定位职责和承诺；设计记录用于追踪取舍；书稿分析用于帮助理解。历史记录需要与当前实现核对。

如果设计动机没有明确记录，书中应写明这是基于实现的分析。命令、配置、默认行为和实验结果必须针对书稿基线实际验证。

## 六、贯穿全书的设计主题

根据当前架构文档，可以围绕以下主题组织深入研究。各主题在正式章节中都需要补齐源码、测试和实验依据。

| 主题 | 需要讲清的内容 |
| --- | --- |
| 插件组合 | 模型、工具、日志与循环如何通过插件体系协作；业务行为如何挂接扩展点 |
| 注册与释放 | 注册为何属于有生命周期的操作；依赖与消费者按什么顺序结束 |
| 模型可见内容与日志 | 如何从记录重建模型输入；新增上下文需要怎样记录 |
| 持久事实与实时通知 | Session 事件、Agent 事件与能力事件分别承担什么责任 |
| 能力替换 | 服务定义、提供者和消费者如何配合；替换实现能影响哪些功能 |
| 配置组合 | profile、bundle 与覆盖配置怎样形成应用；业务差异放在哪里 |
| 类型与数据验证 | 同进程类型保证与配置、文件、进程、网络输入验证如何分工 |
| 失败与恢复 | 谁报告失败、谁停止依赖操作、怎样表达未知结果与恢复条件 |

每个主题需要包含适用场景、成本与限制，避免将某种设计写成适用于所有项目的通用结论。

## 七、实验与业务实战

### 7.1 贯穿案例：企业问题处理助手

建议以企业问题处理助手为主案例：接收问题 → 查询资料 → 调用业务工具 → 请求人工确认 → 执行任务 → 保存记录 → 展示结果。

案例逐步加入业务数据、外部服务、权限、长任务、协作与界面，持续复用读者已经理解的需求背景。涉及业务写操作时，需要明确审批、重复执行、未知结果与审计记录的设计。

### 7.2 建议实验阶梯

1. 运行并观察一次完整任务，区分模型、工具与 Harness 的责任。
2. 编写第一个插件，验证注册和释放。
3. 使用 profile 与配置组装教学应用。
4. 使用模拟模型观察请求、响应、工具调用与后续请求。
5. 阅读 Session 事件，解释界面状态与模型历史的来源。
6. 增加只读业务工具，并验证参数、结果与错误处理。
7. 增加需要人工确认的业务操作，处理取消和失败。
8. 替换一个能力提供者，观察消费者如何复用接口。
9. 增加后台任务或子 Agent，处理等待、中断与结果汇总。
10. 从 SDK 驱动应用，追踪进程间状态与结果。
11. 增加业务工具卡片或客户端扩展，完成交互状态设计。
12. 构建教学用最小 Harness，并与正式实现对照。
13. 完成业务项目，提交实现、验证和运行说明。

这是实验设计清单，模拟模型、回放器及其他教学设施是否能够复用现有实现，需要在编写时核实；缺失设施应计入配套开发范围。

### 7.3 基础实验与真实集成

基础实验尽量使用模拟模型、固定输入和确定性数据，降低 API 密钥、网络与模型变化带来的学习障碍。真实集成实验单独列出外部依赖、配置、费用因素和已验证范围。

教学用最小实现需要明确简化内容，说明正式项目为并发、恢复、权限、流式与生命周期增加了哪些机制。仓库中的应用实验遵循支持的 `dsh` profile 启动方式。

### 7.4 迁移案例

建议补充研发助手与报表助手作为迁移练习。读者需要重新分析需求、选择扩展点并设计验证，不只是替换工具名称。案例中每项能力都要注明已有支持、组合实现或新增开发。

## 八、编写阶段与交付物

## 九、质量与验收标准

### 9.1 面向初学者

- 依赖知识在使用前解释，首次出现的术语有定义与例子。
- 每章有可观察的学习成果，读者能判断是否完成。
- 主线避免提前引入无助于当前任务的高级细节。
- 练习答案解释关键选择与失败原因。

### 9.2 面向源码准确性

- 每篇标明适用版本，源码引用指向相应基线。
- 行为说明与代码、类型、测试和维护中的文档一致。
- 当前事实、历史取舍、作者分析与计划明确区分。
- 覆盖表如实记录已研究、已讲解、已验证与待补内容。

### 9.3 面向实验与业务开发

- 实验说明前置条件、输入、运行步骤、预期输出、失败处理与清理方式。
- 对写操作、长任务和协作流程检查取消、权限、重复执行与恢复。
- 业务功能验证完整用户流程，包括等待、失败与完成。
- 无法运行的真实集成实验标明未验证范围与原因。

### 9.4 面向维护

- 检查 Markdown 链接、源码路径、示例代码与实验结果。
- 引用已有权威资料，避免复制容易漂移的完整 API 清单。
- 仓库内发布的正式文档遵循所在目录的结构、语言配对与检查要求。
- 验证范围与实际改动匹配，记录执行过的检查与尚未解决的问题。

## 十、版本维护与推荐起步

每次书稿升级先比较代码差异，再定位受影响的章节、实验和索引。旧版本书稿保留适用基线，新版本明确变更范围，避免把不同版本的接口和行为混写。

第一批成果建议限定为“详细目录、全仓库覆盖表、两章样章”。样章分别选择“一次任务的完整旅程”和“第一个业务工具插件”，共同检验整体解释、源码深度与动手体验。

第一批验收重点是读者是否知道自己在学习什么、能否按说明完成实验、能否从现象找到实现，以及能否解释修改为何生效。通过后再按篇扩写，逐步形成完整书稿。
