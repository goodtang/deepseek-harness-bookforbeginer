## 一、需求理解

### 1.1 要解决的问题

读者需要知道一个功能解决什么问题、为什么这样设计、代码如何配合、数据如何流动、失败如何处理，以及业务需求应当从哪里扩展。

只读函数不足以支撑这个目标：读懂局部却拼不出完整任务，是读大型运行时类项目最常见的失败方式。

所以本书必须同时承担四个任务：**顺序学习**（零基础可进入）、**源码研究**（机制可追溯）、**开发查阅**（扩展点可定位）、**业务迁移**（能力可交付）。

### 1.2 把“完全掌握”变成可检验的能力

| 能力 | 读者应能做到 | 验收方式 |
|---|---|---|
| 理解原理 | 解释模型、Agent、工具、循环、上下文与状态的关系 | 用自己的话说明一次任务为什么需要多次模型请求 |
| 看懂架构 | 说明模块职责、依赖方向与扩展位置 | 为一个业务需求画出涉及模块与调用顺序 |
| 阅读源码 | 从用户入口追到请求、工具、事件、存储与显示 | 标出关键入口、类型、实现与测试 |
| 修改实现 | 判断变更影响哪些消费者、协议、数据与文档 | 完成一处影响范围明确的修改并验证 |
| 扩展业务 | 增加工具、插件、适配器、流程或界面 | 在受支持的 profile 启动方式下运行扩展 |
| 独立构建 | 依据原理构建教学用最小 Harness | 演示输入、模型调用、工具执行、记录与输出 |
| 验证交付 | 处理取消、失败、权限、恢复、测试与升级 | 通过业务验收与故障场景验证 |

掌握度分四级：**能讲清 → 能改 → 能造 → 能评**。每一篇都有出口验收，全书设三个 capstone。

### 1.3 “所有代码”的覆盖约定

152 万行 TS、370 个包、2230 个 spec：逐行解释既不现实也无教学价值。本书采用四级覆盖，且承诺范围写进序言，避免读者误预期。

| 覆盖层级 | 范围 | 交付要求 |
|---|---|---|
| 全局定位 | 全部 370 个包与主要非包目录 | 模块索引可查到用途、关系、阅读入口 |
| 核心精读 | 约 4.2 万行（见 2.2） | 关键类型、时序、状态变化、失败路径 |
| 能力分类 | 各类能力实现与适配器 | 共同接口、消费者、各实现的有意义差异 |
| 工程支撑 | 测试、构建、发布、原生与平台实现 | 运行条件、作用、修改后的验证要求 |

承诺：**机制与扩展点 100% 覆盖；单包逐行解释仅限核心精读区；其余按家族模式归纳。**

### 1.4 不写什么

- 不逐行注释全部包，不替代仓库现有参考文档（`docs/subsystems`、cookbook、README）。
- 不写模型训练原理、推理算法本身。
- 不覆盖全部 experimental 包（只讲其定位与扩展方式）。
- 不做 UI 像素级复刻教程，讲交互状态设计与插件化扩展。

## 三、与 Codex 规划稿的关系

### 3.1 采纳（8 项）

1. 十篇结构，数据设计独立成篇。
2. 覆盖表（模块台账）作为一等交付物。
3. 八条设计主题作为螺旋线，每章声明推进哪几条。
4. 单一主线案例“企业问题处理助手”，另配两个迁移案例。
5. 事实 / 记录 / 分析三分；无记录的动机标注“基于实现的分析”。
6. 章节八段模板：问题、前置、最小例子、设计图解、真实源码、取舍、实验、故障自测。
7. A–F 阶段与进入条件。
8. 第一轮成果限定为“详细目录 + 覆盖表 + 两章样章”。

### 3.2 修正（5 项）

1. **补精读预算**：给出 4.2 万行清单与四级覆盖，否则 M0 无法验收。
2. **实验设施先核实**：`pnpm run mock:llm` 与快照回放已验证可用，实验按“无密钥、确定性”设计（见第八节）。
3. **首章防劝退**：`1.1` 采用黑盒演示 + 术语悬置 + 观察表，不展开内部机制。
4. **覆盖表降本**：骨架由脚本从 `package.json` 与 `docs/module-graph.md` 生成。
5. **时间不写死**：精简版 25 万字（6 周）→ 完整版 65–70 万字（4–5 个月），以样章试读校正。

### 3.3 保留分歧（3 项）

1. 章节数固定为 52 章（而非“篇级目录待定”），便于排期与覆盖校验。
2. 案例 1 主线 + 2 迁移，放弃四案例并列的广度。
3. 覆盖承诺只对“机制与扩展点”成立，逐行解释仅限精读区。

## 六、教学法

### 6.1 八段式章节模板

| 环节 | 必须回答 |
|---|---|
| 问题与目标 | 解决什么问题，学完能做什么 |
| 前置知识 | 依赖哪些概念，缺了去哪补 |
| 最小例子 | 能否用一个小而完整的例子观察机制 |
| 设计与图解 | 谁负责什么，控制、数据与生命周期如何联系 |
| 真实源码 | 入口、类型、实现、消费者、测试分别在哪 |
| 设计取舍 | 收益、成本、适用条件，证据来自哪里 |
| 动手实验 | 改什么、怎么跑、预期看到什么 |
| 故障与自测 | 如何制造失败、定位、恢复并证明理解 |

正文只用中文解释关键代码，长代码给稳定源码链接与阅读范围；首次出现的术语给中文解释并附原名。

### 6.2 实验阶梯（13 级）

1. 运行并观察一次完整任务，分清三方责任。
2. 写第一个插件，验证注册与释放。
3. 用 profile 与配置组装一个教学应用。
4. 用模拟模型观察请求、响应、工具调用与后续请求。
5. 读 Session 事件，解释界面状态与模型历史的来源。
6. 增加只读业务工具，验证参数、结果与错误处理。
7. 增加需要人工确认的写操作，处理取消与失败。
8. 替换一个能力提供者，观察消费者如何复用接口。
9. 增加后台任务或子 Agent，处理等待、中断与结果汇总。
10. 从 SDK 驱动应用，追踪进程间状态。
11. 写一个业务工具卡片或客户端扩展，完成交互状态设计。
12. 构建教学用最小 Harness，并与正式实现逐项对照。
13. 完成业务项目：实现、验证、运行说明、维护说明。

### 6.3 主线案例与迁移案例

- 主线：**企业问题处理助手**——接收问题 → 查询资料 → 调用业务工具 → 请求人工确认 → 执行任务 → 保存记录 → 展示结果。逐篇加能力，不换背景。
- 迁移一：研发助手（终端、LSP、评审子代理）。
- 迁移二：报表助手（定时、批处理、交付物）。

每个业务能力标注“已有支持 / 组合实现 / 新增开发”，不把“未来可以做”写成“已支持”。

### 6.4 三条阅读路径

| 路径 | 读者 | 顺序 | 预估 |
|---|---|---|---|
| 零基础线性 | 学生 | 一 → 十，逐章实验 | 20 周（每周 3 章 + 实验） |
| 工程师速通 | 有经验开发者 | 1.3 → 2.2–2.5 → 3.1–3.2 → 4.2–4.5 → 5.1–5.2 → 6.1 → 7.1 → 8.3 → 9.1 → 10.x | 6 周 |
| 二开查阅 | 要交付业务 | 10.1 → 6.1 → 4.5 → 3.3 → 9.3，按需回跳 | 2 周出原型 |

## 七、源码研究方法

### 7.1 覆盖表字段

每个模块一行：源码路径、职责、关键入口、核心类型、依赖、消费者、相关事件或存储、所属章节、讲解深度、配套实验、验证证据、待研究问题。

骨架由脚本生成（`packages/*/*/package.json` + `docs/module-graph.md`），人工只填后四列。

### 7.2 覆盖状态由证据决定

- 未读过的模块标“未研究”，不得写成“已覆盖”。
- 无法确认的行为列入问题清单，不以推测填补。
- 每条机制至少有一种证据：实跑输出、源码路径、测试用例、维护文档。

### 7.3 完整流程串联

至少研究八条流程，每条都看控制流、数据流、资源生命周期：用户输入、提示与工具装配、模型流式响应、工具执行与记录、取消、恢复、多 Agent 协作、客户端更新。

## 八、实验基础设施（已核实）

| 设施 | 用途 | 用法 |
|---|---|---|
| `pnpm run mock:llm` | 可脚本化的 Messages/SSE 模拟端点，支持断流、限流、畸形分片、工具调用 | `--port 8000 --api-key mock-key --sequence ...` |
| 真实 profile 接模拟模型 | 无密钥跑完整链路 | `DEEPSEEK_BASE_URL=http://127.0.0.1:8000/v1 DEEPSEEK_API_KEY=mock-key pnpm dsh --profile headless "..."` |
| 快照回放 | 确定性复现会话与 Web 行为 | `pnpm run test:snapshot`、`pnpm run test:web:built` |
| 快照夹具 | 205 份已录制会话 | `snapshots/` |
| 源码启动 | 读者改代码即生效 | `corepack pnpm run start:web` / `dev:web` |

原则：**基础实验一律无密钥、离线、确定性**；真实模型实验单独成节，列出费用、网络与已验证范围。

## 九、质量与验收

### 9.1 面向初学者

- 依赖知识在使用前解释，术语首次出现有定义与例子。
- 每章有可观察成果，读者能判断是否完成。
- 主线不提前引入当前任务用不到的高级细节。

### 9.2 面向源码准确性

- 每篇标注适用版本，源码引用指向基线提交。
- 行为说明与代码、类型、测试、维护文档一致。
- 事实、历史、分析、计划四类内容明确区分。

### 9.3 面向实验

- 每个实验写明前置条件、输入、步骤、预期输出、失败处理、清理方式。
- 写操作、长任务、协作流程必须检查取消、权限、重复执行与恢复。
- 无法运行的真实集成实验标明未验证范围。

### 9.4 自动校验（防止腐烂）

- 引用路径/符号存在性检查（脚本扫描书稿中的 `packages/...` 与 `ctx.*`）。
- 代码块编译检查（沿用仓库 `doc-typecheck` 思路）。
- 实验可运行检查（CI 跑一遍 lab 清单）。
- 术语一致性检查（术语表为唯一来源）。

## 十一、风险与对策

| 风险 | 表现 | 对策 |
|---|---|---|
| 规模失控 | 想讲完 152 万行，进度停滞 | 四级覆盖 + 精读预算写进序言 |
| 概念过载 | 零基础读者首章放弃 | 黑盒旅程 + 术语悬置 + 观察表 |
| 实验不可跑 | 依赖密钥、网络、模型波动 | mock LLM + 快照回放，全部确定性 |
| 覆盖表腐烂 | 370 行手工维护 | 脚本生成骨架，只填三列 |
| 与仓库文档重复 | 两处事实开始分叉 | 事实指向权威页，书只写顺序与动机 |
| 代码演进 | 路径与接口过期 | 版本锚定 + 自动校验 + 每季度回归 |
| 单人视角偏差 | 解释像“作者自述” | 事实/分析标注 + 试读验收 |
