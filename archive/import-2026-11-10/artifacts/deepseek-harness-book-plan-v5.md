## 摘要

一本好的源码书，应该让读者越来越敢于打开真实代码。最初，他只能看到界面上出现了一段回答；后来，他能沿着请求找到循环、工具和事件；再后来，他能判断一个业务需求应该改哪里，解释自己的设计，并用测试确认它确实有效。

这本书以 DeepSeek Harness 为研究对象，从零基础出发，带读者走完这段过程。正文用具体任务串起原理，源码精读解释关键机制，图解帮助读者建立并检验理解，实验把理解变成能力，模块索引承接全仓库查阅。书中的每一次深入，都应当回答读者已经产生的疑问。

全书以中文写作，技术术语首次出现时说明原名。阅读体验、技术准确性和独立开发能力共同决定内容是否合格。

## 一、读者最终要获得什么

### 1.1 从看见结果，到解释结果

读者不需要带着框架开发经验开始学习。书中先帮助他观察一次任务，再解释程序、模块、异步执行和事件等基础知识，逐步进入框架内部。

学完后，读者应能沿着一次用户操作说明：应用怎样启动，输入怎样进入 Agent，模型收到哪些内容，工具怎样执行，状态怎样记录，界面怎样更新，以及失败后由谁处理。他还应能据此增加业务能力，并对自己的修改提供验证证据。

### 1.2 能力目标

| 能力 | 达成表现 | 验收材料 |
| --- | --- | --- |
| 能解释 | 用自己的语言说明模型、Agent、工具、循环与会话的关系 | 一份任务流程讲解，能回答后续追问 |
| 能追踪 | 从用户入口找到类型、实现、消费者、记录和显示 | 带源码坐标的流程图与观察记录 |
| 能修改 | 判断变更影响并完成一个明确功能 | 修改、相关测试与兼容性说明 |
| 能扩展 | 为业务选择工具、服务、配置、协议或客户端扩展方式 | 可运行的业务功能及设计说明 |
| 能构建 | 独立实现教学用最小 Harness，解释与正式实现的差异 | 最小实现、演示与差异清单 |
| 能交付 | 处理权限、取消、重复执行、未知结果、恢复与升级 | 综合项目、故障验证与运行手册 |

能力分级采用“能讲清 → 能改 → 能造 → 能评”。阅读完章节不自动等于掌握，需要经过操作、解释和迁移练习。

### 1.3 全仓库覆盖的范围

所有模块都有定位、职责、依赖和阅读入口；关键机制深入到实现与失败路径；相似提供者说明共同接口与差异。应用、SDK、原生能力、构建与测试设施也进入范围清单。

实验性模块保留完整定位，按研究价值选择深入程度；第三方与 vendored 实现讲清本项目依赖的机制，精读其中影响框架理解的部分。模型训练与推理算法的完整实现不属于本书范围。

覆盖清单必须区分“建立索引”和“完成讲解”。只有清单、章节与验证相互对应，才报告覆盖完成情况。全书不以逐行转述作为完成标准。

## 二、整本书怎样讲才好读

### 2.1 让读者先在意这个问题

每章从一个具体、可理解的场景开始。读者应知道事情发生在哪里、谁遇到困难、为什么值得解决。背景只保留理解问题需要的部分，不虚构事故、测量结果或作者经历。

讲工具执行，可以先让企业助手查询一张工单；讲取消，可以让查询正在等待远端返回；讲恢复，可以观察应用重新启动后哪些信息还在。先建立需要，再介绍机制名称。

### 2.2 用连续的发现维持阅读兴趣

章节的基本推进是“看到现象 → 作出预测 → 运行观察 → 解释原因 → 对照源码 → 尝试改变”。每次只提出当前最值得解决的问题，回答后再进入下一层。

读者的错误预测也有价值。例如，他可能以为按下停止就能撤回已经发出的业务请求。实验应帮助他分清本地取消、远端执行与结果确认，而不是把错误答案写成用来衬托作者的笑话。

段落之间需要有因果联系：上一段指出的问题，由下一段的方法解决。避免在叙述中连续插入互不相关的定义，也避免每一小节都用同一种设问开头。

### 2.3 用成熟、自然的中文解释技术

- 以读者为交流对象，适度使用“你”和“我们”，避免机械地重复。
- 先说明作用，再给名称；抽象概念后紧跟小例子，关键术语前后一致。
- 一段推进一个主要意思，长短句交替，让解释有停顿，也能连续读下去。
- 原理与过程用连贯文字讲清；比较用表格；步骤用编号；图只承担文字难以表达的关系。
- 代码标识保留原名，解释使用准确中文；不用中文译名取代读者实际需要搜索的符号。
- 直接说明行为、条件、责任与结果。避免“显然”“很简单”“一看就懂”等给初学者施压的词。
- 不用“魔法”“黑科技”“颠覆”等词制造兴奋，不以人格化故事或夸张比喻替代机制。
- 不使用反复对立的句式、成串口号、每段加粗结论或频繁感叹来催促读者。

技术准确性优先。不能为了流畅删去取消条件、异常路径、数据归属和兼容性限制；应调整讲述顺序、增加例子，让这些内容变得可理解。

### 2.4 给阅读节奏留出变化

一章可以从操作开始，也可以从一段短日志、一张状态图或一个业务需求开始。八项教学内容都需要覆盖，但不要求每章机械使用相同的八个小标题。

代码每次只展示当前解释需要的连续片段，交代输入、输出、所在位置和调用者。完整实现保留稳定链接。读者完成预测、修改或解释后，再给答案，避免正文替他完成全部思考。

高级内容放在明确标注的进阶阅读或参考页中，主线只引入当前需要的知识。所谓循序渐进，包括让读者知道哪些细节暂时可以放下，以及何时会回来理解。

### 2.5 一章需要完成的承诺

章节开头说明读者将解决什么问题；正文兑现这个承诺；结尾用简短的实验结果与解释检验理解。当前问题必须得到回答，延伸阅读不能替代答案。

下一章从本章真实留下的限制继续。例如，工具已经能执行，但如果应用退出后任务记录消失，就自然需要学习持久化。这样的衔接比“接下来更精彩”更能让读者愿意继续。

### 2.6 把风格变成可检查的要求

| 检查点 | 合格表现 |
| --- | --- |
| 开篇 | 不熟悉源码的人也知道场景、困难与本章目标 |
| 术语 | 首次使用有解释，读者不需要猜缩写 |
| 连贯 | 能说出相邻两节为什么按这个顺序出现 |
| 实现 | 能把代码片段对应到前面的问题，而不只是复述语句 |
| 取舍 | 说明收益、成本与适用条件，有依据或明确标为分析 |
| 结尾 | 当前问题已解决，下一步学习有实际理由 |
| 试读 | 读者愿意继续，且能复述与独立完成任务 |

“欲罢不能”是阅读体验目标，不能由作者自评保证。试读同时观察兴趣、理解和独立操作，不能只问读者是否觉得文笔好。

## 图解教学与插图规范

### 图文共同承担教学任务

插图、图表和流程图是教材的核心组成部分。它们帮助学习者看清参与者、顺序、状态、数据和责任，再把这些认识对应到源码与实际操作。关键机制的讲解应在文字、图和实验之间建立联系。

读者学完一次工具调用，应当能沿着图说明发生了什么，找到对应代码，并预测改变输入后的结果。只看图能记住几个名字，或者只看代码能复述几条语句，都还不足以证明理解。

配图不按页数或字数机械分配。涉及多方交互、循环、状态切换、数据变换、资源释放或跨层更新时，需要明确评估图解需求；复杂关系仍然只能靠长段文字解释的章节不能直接通过验收。

### 先确定学习问题，再选择图形

| 学习者的疑问 | 合适的表达 | 需要避免的误导 |
| --- | --- | --- |
| 哪些部分在一起，分别负责什么 | 架构图、职责分区图 | 把教学分层画成实际代码必须遵守的依赖层级 |
| 一件事先后经过哪里 | 流程图 | 用空间位置暗示所有节点严格串行 |
| 几个参与方如何交换消息 | 时序图、泳道图 | 把通知当作同步调用，或省略等待与取消 |
| 当前处于什么状态，什么会触发变化 | 状态图 | 把多个可并存的状态维度混为一组互斥状态 |
| 输入如何变成请求、记录和显示 | 数据流图、数据变换示意 | 把传输、持久化与派生视图画成同一种存储 |
| 数据由谁保存，怎样关联和读取 | 数据模型图、字段示例、归属表 | 把教学概念关系当作真实数据库表结构 |
| 谁创建、使用并释放资源 | 生命周期图、资源归属图 | 只画创建，不画失败和卸载时的结束顺序 |
| 两种机制或结果有什么差异 | 对照图、对比表、前后快照 | 把不同输入条件下的结果直接比较 |
| 操作发生在界面哪里，怎样变化 | 带标注截图、连续界面状态图 | 把设计草图当作已实现、已验证界面 |
| 性能、耗时或资源怎样变化 | 曲线、柱状图、分布图 | 使用没有测量依据的数字或没有单位的坐标 |

一张图先解决一个主要问题。需要同时讲依赖、调用顺序和数据流时分图表达，使用一致的名称互相引用，避免制作一张难以阅读的全仓库大图。

### 总览、展开与证据三个层次

第一次介绍任务时，用少量节点给出概念总览，只说明角色与主要关系。进入具体章节后，展开当前环节，增加请求、分支、事件或状态。精读与实验时，再提供与代码或观察记录对应的细图。

每层都标明简化范围。概念图不能被当作完整调用链；代码流程图不能省略会改变结果的关键分支。图中使用真实符号时，记录对应源码基线与位置；教学名称首次出现时说明与真实实现的对应关系。

同一主线案例反复出现时保留相同的角色名称与视觉位置，新增内容作局部突出。先给读者独立可读的完整图，再提供前后对照，避免依靠翻找上一张图才能理解当前图。

### 每张图怎样进入正文

正文先交代即将解决的问题，再在第一次需要时展示图。图后给出简短读法，解释起点、箭头和本图结论；随后沿着图进入代码或实验。避免在一页上堆放若干张没有解说的图。

每张图包含稳定 ID、标题、图注、图例、适用基线、简化范围和源码或实验依据。图注说明读者应从中看出什么，不只重复标题。正文引用图 ID，读者可以据此找到解释、源文件与更新记录。

例如，V10 可以先给一段假设执行记录，让读者预测其中有几个 turn、几个 step、几次请求；再用分层时间线逐步标注。正式版本必须以实验记录与当前实现校正三者关系，不能先画出等同关系再让代码适配图。

### 图解也需要学习者动手

部分图先让读者预测下一条边、补全一个状态或给事件排序，再展示完整解释。图解练习的目标是帮助理解，不把关键说明藏在答案中。

源码精读使用图中的序号对应代码位置，实验记录使用同一组角色与事件名称。读者运行后回到图上标出实际路径，包括失败路径。若实际结果与图不同，先检查假设与证据，不能忽略差异。

### 图形、截图与图表的制作原则

结构关系、时序和状态优先保留可版本管理的图源，例如 Mermaid；需要自由排版的概念插图保留可编辑矢量源。PNG 截图保留原图与独立标注信息。复杂图是否采用 draw.io 等工具，在制作时按编辑需求决定。

使用统一的字体、角色名称、图例和方向。控制流、数据流、通知、依赖等连线含义明确；同一图内不要让箭头无说明地同时代表多种关系。优先减少交叉与层层嵌套，过长的图拆成有导航关系的小图。

颜色只作辅助，角色与状态同时用文字、线型或符号区分。字号按网页正常阅读和 PDF 实际版面检查；不要把整张大图缩小到文字无法辨认。灰度打印后也应能区分主要关系。

截图记录版本、窗口尺寸、操作步骤和对应实验，清除凭据与个人业务资料。设计草图明确标注为草图；真实截图需要与运行结果一致。只有需要展示实际产品行为时才使用截图，结构关系仍用结构图解释。

统计图记录数据来源、测量条件、单位、样本和限制。假设数据可以用于讲解，但必须标为演算示例，不能作为项目性能结论。AI 生成的装饰性插图不能承担需要精确关系、文字和数据的技术说明。

### 网页与 PDF 都需要真正看过

网页阅读版可提供放大查看与图组逐步展开，默认视图本身仍需可读。PDF 导出包含完整静态图、图注与阅读顺序，不能依赖悬停、动画、折叠或外部网站才能理解。

每图提供替代文本和附近的文字解释。图源、网页渲染和 PDF 分别检查连线、裁切、中文字体、对比度、图注与分页，保留图与解释尽量相邻。渲染成功不等于读者看得清，需要实际打开检查。

### 图的维护与完成条件

图表清单记录 ID、教学问题、所属章节、类型、图源与输出、代码基线、证据、简化项、替代文本和审核状态。源码关系变更时定位受影响图，图源与书稿一同更新。

图解审校分为三个层次：语法与引用检查；与源码、协议和实验的语义核对；网页和 PDF 的视觉及初学者试读。自动检查不能证明箭头含义正确，也不能代替实际看图。

一张关键图完成时，读者应能借助图找到参与者和起点、解释主要关系、追踪一次正常路径，并在涉及失败的章节找到相应分支。每章验收增加“关键图完整、图文一致、可读且有证据”这一项；无需配图的短基础单元，记录无需配图的理由即可。

## 三、语言风格试写

以下两段用于展示正文语气。场景为教学设定，没有声称已经运行对应实验；正式样章需要补上基线、输入、源码坐标与运行证据。

### 3.1 开篇试写：一句请求发出去以后

假设你第一次打开这个项目，想让它帮忙查一张工单。你输入：“看看 1042 号工单为什么还没处理。”界面开始出现文字，接着显示一次工具调用，最后给出答复。

从使用者的角度看，这件事很自然：提出问题，等待答案。但如果现在要你加一个功能——在答复之前，把处理建议交给负责人确认——你会把代码写在哪里？

直接修改模型请求似乎可行，可负责人可能过十分钟才回复。修改工具也有道理，但并不是每次查询都需要确认。再考虑一步：等待期间关闭应用，重新打开后，这次确认还在吗？

一个小需求，把模型、工具、等待状态和数据保存联系到了一起。要把它做好，我们需要知道这几个部分怎样配合。

现在先不用记住包名，也不用打开最长的那个文件。第一件事，是把刚才的任务再看一遍。这次我们留意三个问题：什么时候向模型发送了请求，什么时候真正执行了查询，查询结果又怎样进入下一次请求。

在配套实验里，你会先使用准备好的响应脚本运行这个过程。它让我们控制返回内容，逐步观察每个环节。等你能指出模型负责哪一步、程序负责哪一步，再打开源码，就会知道自己正在寻找什么。

这一章结束时，你不需要解释整个仓库。但你应该能够画出这次任务经过的几个主要环节。那张图会在后面的章节里越来越具体。

### 3.2 原理试写：按下停止之后，什么停下了

企业助手正在提交一项业务变更，你忽然发现选错了工单，于是按下停止。界面不再显示新的内容。

工单有没有被修改？仅凭界面停下来，还不能回答。

请求可能尚未离开本机，也可能已经到达业务系统。甚至业务系统已经完成修改，只是响应还在返回途中。如果这时直接重试，你可能提交第二次；如果直接显示“已取消”，又可能让使用者误以为业务没有变化。

因此，我们需要分别确认两件事：当前执行是否停止，以及远端操作的结果是否已知。前者属于执行控制；后者需要业务系统提供可以核查的依据。

这一节的实验会使用可重置的本地业务服务，分别安排“提交之前取消”和“提交之后尚未收到响应”两种情况。你要先预测工单状态，再从服务端读取实际结果。之后，我们才沿着源码检查取消信号如何传播，以及未知结果如何被表达。

当你能解释这两个结果为什么不同，就已经开始具备业务开发需要的判断力。下一步，是设计一个即使收到重复请求也能识别同一次操作的业务接口。

## 四、学习路线与基础准备

### 4.1 先体验，再由底层深入

主路线为：一次完整体验 → 基础准备 → Cordis → 启动组合 → 最小会话知识 → Agent 循环 → 数据进阶 → 能力扩展 → 协作 → 协议与交互 → 业务交付。

开篇体验使用准备好的环境和脚本，允许读者暂时只会操作。随后需要独立安装、阅读和修改时，再补齐相关知识。基础单元是正文的一部分，不把零基础读者引向一串没有讲解的外部链接。

### 4.2 基础单元及进入条件

| 单元 | 学习内容 | 需要独立完成的操作 | 后续用途 |
| --- | --- | --- | --- |
| F1 程序如何运行 | 命令、路径、工作目录、文件和进程 | 找到输出与错误，区分相对路径和绝对路径 | 环境准备与启动 |
| F2 数据与函数 | 变量、对象、数组、函数、返回值 | 写一个工单查询与格式化函数 | 阅读模块 |
| F3 类型与分支 | 类型、接口、联合类型、收窄 | 处理成功、失败和未知结果三种情况 | 服务、事件与协议 |
| F4 模块与依赖 | ESM、导入导出、包与工作区 | 拆分并连接两个模块 | 插件与工程布局 |
| F5 异步执行 | Promise、async/await、顺序与并发 | 等待结果并解释执行顺序 | 模型、工具与 RPC |
| F6 错误与取消 | 异常传播、finally、取消信号、清理 | 中止等待并验证资源释放 | 生命周期与恢复 |
| F7 测试与调试 | 断言、断点、日志、失败定位 | 先观察失败，再修正并解释原因 | 实验验证与二次开发 |

F1–F7 分阶段穿插在第一篇中，F8 在协议与客户端前补充。各章列出基础单元依赖及补学入口；已具备基础的读者可通过练习跳过讲解。

### 4.3 三条阅读路径

学生路径按主线学习并完成基础练习；工程师路径通过基础自测后进入框架与循环；业务查阅路径从需求选择扩展点，再返回对应机制和实验。三条路径共享数据与生命周期知识，不能只学工具注册就直接承担业务写操作。

阅读时长在试读后按学习、实验、排错和项目四类投入估算，不承诺固定周数。章节数量也不代替难度评估。

## 五、全书候选目录

以下为可调整的篇章目录。篇号表示教学组织，未声称仓库存在同名分层。正式章号在学习依赖与样章验证后确定。

### 第一篇：从一张工单开始

1. 一句请求发出去以后：观察完整任务，区分模型、工具和 Harness。
2. 第一次自己运行：路径、进程、开发环境与准备检查。
3. 把数据交给函数：用工单小程序学习变量、对象和函数。
4. 让代码可以组合：类型、模块、包与工作区。
5. 当结果不会立刻返回：异步、错误、取消与测试基础。
6. 打开真实仓库：从需求找到入口，建立第一张源码地图。

出口成果：能运行入门实验，读懂小模块，并解释一次任务的主要环节。

### 第二篇：插件怎样组成一个应用

1. 从增加一个能力开始理解插件。
2. Context 怎样连接插件与服务。
3. 服务定义、提供者与消费者怎样协作。
4. 事件的不同调用方式怎样影响扩展。
5. 插件卸载时，谁负责结束工作和释放资源。
6. 配置校验与重载：哪些失败必须尽早暴露。

出口成果：写出可替换服务和消费插件，验证注册、依赖与释放。

### 第三篇：从启动命令到运行中的插件树

1. 应用从哪里进入，何时算启动完成。
2. profile 怎样保存应用组合，运行时数据存在哪里。
3. bundle 与 patch 怎样叠加和覆盖。
4. Web、headless、SDK、sdk-minimal 与 ACP 怎样选择。
5. 查看实际配置，并定位一项启动故障。

出口成果：使用受支持的 profile 启动方式组装教学应用，说明配置来源。桌面专属组装在第九篇深入。

### 第四篇：一次任务为什么需要一个循环

1. 先认识会话：事件、消息与模型历史的最小知识。
2. Agent 接口与运行中的注册表。
3. turn 与 step：任务怎样进入、继续与结束。
4. 输入认领、队列和插入的新消息。
5. 提示与工具声明怎样进入请求。
6. 工具调用怎样经过执行管线。
7. 模型流式响应、失败重试与取消传播。
8. 亲手构建最小循环，并与正式实现对照。

出口成果：完成综合项目一，追踪请求、工具、记录与取消。最小循环采用内存记录，持久化与重启恢复在第五篇增加。

### 第五篇：程序退出后，什么应该留下

1. 从事件记录解释已经发生的事情。
2. 投影怎样把记录变成可读状态。
3. 持久化提供者、格式识别与版本迁移。
4. 重启、重新附着与中断任务分别怎样处理。
5. 上下文压缩、请求历史与计量。
6. 会话、设置、凭据、附件、工作区与业务数据库的归属。

出口成果：解释状态来源，完成一项投影实验和一个受控恢复实验，核对保存前后的业务与会话状态。

### 第六篇：把工具接到真实业务

1. 一个新需求应该落在工具、服务还是提供者。
2. 文件、工作区与执行环境怎样配合。
3. subprocess、Shell、持久终端与 SSH 的分工。
4. 沙箱与审批怎样约束操作。
5. Web、LSP、MCP 与技能怎样参与任务。
6. 后台任务、调度、目标、待办与计划。
7. 附件、交付物与其他能力家族的查阅方法。
8. 业务写操作：确认、重复请求和未知结果。

出口成果：完成综合项目二的业务执行部分。能力家族是否足够承接全部模块，由覆盖清单检查，不能由目录名称推断。

### 第七篇：让多个 Agent 共同完成任务

1. 子 Agent 怎样创建，谁拥有它的资源。
2. 消息、发现、等待、中断与结果传递。
3. 预算与失败怎样影响父级任务。
4. 团队任务板与工作流分别解决什么问题。
5. preset 怎样形成可复用的业务组合。

出口成果：为综合项目二增加协作，验证等待、中断和父级收敛。不同协作机制的实际保证分别从源码核实。

### 第八篇：从另一个程序驱动 Harness

1. 请求响应、流与进程通信的基础准备。
2. Host、API 与 BFF 的职责。
3. 类型、RPC、网关与流式同步。
4. 断线以后，调用方怎样重新知道状态。
5. TypeScript、Python SDK 与 ACP 的使用与实现。

出口成果：从外部程序驱动会话，追踪输入、状态与结果，说明哪些操作发生在不同进程或网络之间。

### 第九篇：让用户看懂并控制执行

1. 界面状态与渲染的基础准备。
2. 客户端启动与插件激活。
3. 会话视图怎样结合记录与实时更新。
4. 工具卡片、提问与人工确认。
5. 等待、取消、失败、重连与恢复的完整交互。
6. 布局、键盘、焦点、响应式、主题与国际化。
7. 桌面应用的组装、平台依赖与构建。

出口成果：为主线案例完成业务工具卡片与人工交互；平台构建作为有条件的进阶实验单独验收。

## 六、贯穿案例与三个综合项目

### 6.1 主线：企业问题处理助手

主线从只读查询开始，逐渐加入资料检索、处理建议、人工确认、业务写入、协作、持久记录与界面。工单业务使用可重置的本地模拟服务，避免入门依赖真实企业账号。

业务服务保存工单的权威状态；Harness 组织模型、工具、执行与会话；人工确认表达被确认的具体操作；客户端负责让用户理解状态并采取行动。模型可以提出建议，但业务权限与规则由确定性代码执行。

所有业务能力标记为“已有能力、组合实现或配套新增”。规划中出现需求，不表示仓库已经提供完整实现。

### 6.2 综合项目一：能够解释的最小任务系统

输入是查询工单的请求及可控模型响应。输出是查询结果、执行记录和一份流程解释。读者先使用正式组合观察，再独立实现教学用最小循环。

验收需要覆盖多次模型请求、一次工具调用、无工具的答复与取消；能指出模型请求内容来自哪里，并解释教学实现省略的持久化、并发与权限机制。所需模拟设施与脚本由配套项目实现或复用后验证。

### 6.3 综合项目二：能够控制的业务执行

输入是带权限与确认要求的工单修改任务。输出是可核查的业务状态、确认记录、执行结果与协作报告。

验收包括只读权限拒绝写入、确认与实际操作一致、重复请求识别、取消后的状态核查、响应丢失时表达未知结果，以及子 Agent 失败后父级正确结束或报告。涉及幂等的能力由模拟业务服务与业务插件明确实现，不能假定 Harness 自动提供。

### 6.4 综合项目三：能够交付的业务应用

输入是一份包含业务需求、用户角色和运行条件的项目说明。输出是可运行应用、SDK 或 Web 入口、工具卡片、持久数据、故障验证报告和运行手册。

验收要求另一位读者按手册完成环境准备、运行、正常操作、失败复现、重启核查与版本升级。未取得目标平台或外部服务时，明确列出尚未验证的范围。

### 6.5 迁移练习

研发助手练习终端、LSP 和评审协作；报表助手练习调度、批处理与交付物。读者需要重新划分业务责任并选择扩展点，提交一项与主案例不同的设计理由及验证证据。

### 7.2 自动提取与人工审核分工

基础盘点依赖 Git 跟踪文件清单、包清单和维护中的文档，不依赖 CodeGraph。脚本使用 `git ls-files` 获得基线文件范围，从 `package.json` 读取包名与各类显式依赖，再关联文档路径；`docs/module-graph.md` 只作为 peer dependency 共享实例关系的辅助资料，不能当作完整运行时依赖图。

CodeGraph 可用时，按仓库规则优先用它查询符号、调用与影响关系；不可用时，基础盘点继续运行，符号和动态关系标为待解析。后续可用语言解析工具或人工定点阅读补齐，并记录方法。文本搜索只帮助定位，不作为完整调用关系证据。作者审核职责、动态关系、机制解释、章节安排与验证证据；自动结果包含来源和基线，不能把推断字段标为人工核实。

源码坐标使用仓库相对路径、符号名和提交哈希。展示时可以缩写包名；运行时目录与命令单独记录。没有核实的路径不进入教学操作说明。

### 7.3 覆盖状态与完成标准

状态按“未研究、已定位、已解释、已实践、已验证”记录，同时保存适用深度。只要求定位的模块可以在定位层完成，但不能计入机制实践率。

定位率的分母是基线范围内的模块；机制讲解率的分母是审核后的机制清单；实验验证率的分母是要求实验的条目。每次报告同时列出分子、分母、排除项和未解决问题，避免笼统宣称百分之百掌握。

### 7.4 从流程决定精读范围

至少研究启动、输入认领、请求组装、模型流、工具执行、取消、投影、重启恢复、多 Agent 协作与客户端更新。每条流程都检查控制、数据和资源生命周期。

核心包是研究起点。流程进入重试、上下文、作用域、投影或激活等其他实现时，继续追踪必要代码，不以固定包数或行数截断解释。

### 7.5 事实与设计分析

源码和测试确认行为；维护中的文档说明公开使用方式；设计记录提供取舍依据。缺少原始记录的设计动机写为基于实现的分析，不替作者编造意图。

模型请求的相关输入需要能从会话记录及其解释规则重建。业务数据库、文件和外部服务各有自己的权威来源；执行日志不能自动证明外部操作成功。

## 八、实验设计与验证

### 8.1 分别定义模型凭据、外网与可重复结果

核心实验不使用真实模型凭据，可以使用明确标注的测试凭据。完成依赖准备后，只有通过阻断外网验证的实验才标记为可离线运行。安装、浏览器下载和构建准备的网络需求另列。

可重复验证针对具体断言，而不要求所有时间戳和临时路径逐字相同。并发、时钟、端口与文件影响需要受控；不能为了通过而抹去有意义的状态差异。

### 8.2 三种实验方式

| 方式 | 用来证明什么 | 不能代替什么 |
| --- | --- | --- |
| 模拟模型与故障服务 | 给定响应和协议故障下的行为 | 当前真实模型与业务服务的集成效果 |
| 已录制会话回放 | 已有输入场景的记录与显示符合预期 | 未录制的新业务行为与任意交互 |
| 真实集成 | 当前外部系统、模型或平台下的功能 | 所有故障组合的可控验证 |

模拟服务按请求到达顺序消费脚本。并发会话需要独立实例或受控顺序；固定随机种子不能单独保证每个会话获得相同故障。

### 8.3 每个实验的最小说明

每项实验记录 ID、目标、知识依赖、基线、平台、环境准备、输入、步骤、预期结果、断言、失败场景、清理与证据位置。临时 Harness home、工作目录、端口、环境变量和进程归属必须明确。

运行步骤分别说明 PowerShell 与适用的其他 shell。涉及源码、构建产物、`start:web` 与 `dev:web` 时，写清构建与更新条件；正文只发布在目标环境运行验证过的命令。

### 8.4 基础实验编排

| 实验组 | 内容 | 所属学习阶段 |
| --- | --- | --- |
| L01–L03 | 黑盒观察、基础练习、第一次插件加载与卸载 | 第一、二篇 |
| L04–L05 | profile 组合、最小会话与请求观察 | 第三、四篇 |
| L06–L07 | 工具循环、教学最小实现与取消 | 第四篇、综合项目一 |
| L08–L09 | 投影、持久化与受控重启恢复 | 第五篇 |
| L10–L11 | 能力替换、确认写入与结果核查 | 第六篇 |
| L12 | 子 Agent 等待、中断与父级收敛 | 第七篇、综合项目二 |
| L13–L14 | 外部程序驱动、业务卡片与人工反馈 | 第八、九篇 |
| L15–L16 | 干净环境交付、迁移案例 | 第十篇、综合项目三 |

实验组可以包含多个小练习。正式清单需要逐项拆分断言；表格本身不表示设施已经存在。

### 8.5 验证外部结果并精确命名恢复

业务修改后重新读取业务状态，文件操作后检查文件，卸载后检查注册项与进程，界面交互后检查实际显示和可访问行为。Agent 自述只属于输出的一部分。

请求重试、会话重新附着、进程重启、格式迁移和业务补偿分别编写实验。它们的前置状态、保证与失败后处理方式不同，不能以一句“恢复成功”合并验收。

### 8.6 设施与证据的当前状态

仓库提供模拟 LLM 服务、会话回放及相关脚本入口。当前能够沿用的证据是文档及部分实现检查、前次模拟服务帮助命令成功退出；这些证据仅证明设施与入口的部分情况。反馈中报告的命令试跑和历史规模统计先保留出处，原始脚本、输入与输出核对后才能升级为本教材的验证证据。样章场景实测必须按下节执行，当前状态为待执行。

每项正式实验保存基线、平台、命令、断言、输出或报告、退出状态、清理结果和未验证范围。真实模型、外部业务与平台专项单独标注条件；基础 CI 不默认承担所有集成实验。

## 开工证据与闭环样章验收

### M0：在详细目录背后建立可核对的范围

M0 交付三类清单骨架，同时提交首批已经填充并审核的机制清单、精读范围初稿、可复跑统计脚本及其报告。清单从启动、会话、循环、工具、取消、恢复、协作、协议与界面等关键流程展开，标明涉及模块、重要类型、失败路径、章节、图组与实验。

精读范围按完整流程确定，包含关键提供者与消费者。尚未解决的符号、动态关系或跨平台行为列为未解析，说明它会影响哪一章，不能因为有包名和路径就视为已经研究。

#### 可复跑统计的交付要求

统计脚本本身属于 M0 交付物，随报告保存脚本版本、代码提交、工作树状态、文件范围、排除项、匹配规则与原始输出。当前规划没有实现该脚本，也没有重新执行全仓库统计。

| 指标 | 必须说明的口径 |
| --- | --- |
| 包与分组 | 是否只计 `packages/*/*/package.json`，是否含私有包、应用与 vendor，分组如何计算 |
| 源码行数 | 物理行或有效代码行，包含哪些扩展名，是否计入测试、生成文件、声明文件和 vendored 内容 |
| 测试文件 | 使用哪些文件名规则，单元与集成文件是否合并，按文件数还是用例数 |
| 快照夹具 | 按场景、会话、父子角色还是文件计数，历史格式代际如何处理 |
| 精读范围 | 精读文件清单、选择理由、是否含测试，以及由哪些关键流程引入 |

用户提供的历史统计可作为待复核参考值。复跑与历史结果不同，先比较提交与统计口径，不为了对齐数字修改范围。缺少历史脚本时明确新旧口径暂不可直接比较。

脚本需要在没有 CodeGraph 的环境完成文件、包、依赖类别与已有文档的基础清单。它不保证自动生成完整机制清单；后者仍需按源码和测试审核。不得为了降级盘点绕过当前工作区在 CodeGraph 可用时的查询规范。

#### 第一次预算与范围校准

M0 报告把每篇关联到机制数量、精读文件、所需基础知识、图组、实验和平台条件，再与第九节预算对照。源码行数用于估计研究投入，不用统一的“每行代码对应多少字”推算教学篇幅。

对明显超载的篇章，选择拆分、转入进阶参考或调整预算，并记录仍未覆盖的内容。M0 完成条件是主要学习成果都有机制、精读范围和验证安排，预算矛盾已解释；清单尚有未知项时逐项说明是否阻塞样章。

### M1：样章二必须完成一个教学闭环

《第一个业务工具》需要交付完整图文样章与可复现的配套实验。它从一个具体查询需求出发，介绍必要知识，进入真实实现，完成一项可运行的工具改动，解释输出，再用独立断言核查结果。

环境准备与基础补课是进入条件，不能替代源码部分；风格试写也不能替代闭环样章。独立基础知识较多时可以提供前置单元，但样章必须明确指回已经讲解的必要知识。

| 样章组成 | 必交内容 | 验收标准 |
| --- | --- | --- |
| 问题与预测 | 业务输入、读者预测、预期观察 | 不熟悉框架的人知道要解决什么 |
| 图解 | 任务概览、实际交互时序、状态或数据变化 | 图中关键关系可对应代码与记录 |
| 源码 | 仓库相对包路径、符号名、基线提交、经核实的行号与必要阅读范围 | 能从正文定位真实声明、实现和消费者；行号依附指定提交 |
| 可运行改动 | 完整示例文件或补丁、挂接配置、受支持的启动方式 | 按样章步骤能得到同一功能，关键代码没有省略 |
| 断言与输出 | 场景输入、独立断言、真实运行输出与结果解读 | 不以模型自述或仅退出码代替行为验证 |
| 取舍 | 扩展位置、数据和资源责任、限制与依据 | 解释为什么这样做以及什么情况下需要改变 |
| 排错与清理 | 一项失败定位、资源归属与清理证据 | 能判断未完成范围，不遗留自有服务与进程 |
| 迁移练习 | 改变一个查询条件或数据结果的独立练习 | 读者能解释修改为何生效 |

只接受实际运行得到的输出。正文可以为阅读截取输出，但保留完整日志、截取位置及脱敏说明。源码行号用于方便阅读，长期定位仍依赖提交、路径与符号。

### M1 的三组必测场景

三组场景使用同一真实工具和正式执行管线，只替换模型端或必要的本地业务服务。各组独立重置 home、工作目录与模拟脚本，避免前一组结果影响后一组。样章先讲正常过程，再将断流与取消作为两个独立排错实验。

| 场景 ID | 安排 | 必须核查的结果 |
| --- | --- | --- |
| M1-S1 正常工具循环 | 使用可控响应让模型请求真实业务查询工具，再根据工具结果完成答复 | 至少两次模型请求；工具名称、参数和执行次数符合脚本；后续请求包含预期工具结果；会话记录与本地业务查询结果一致 |
| M1-S2 断流处理 | 在声明的请求阶段注入断流，记录所选重试或终止策略及其上限 | 故障确实发生；请求次数和终止状态符合已核实策略；失败片段不会被误判为成功操作；核查工具次数、最终结果、记录与连接释放 |
| M1-S3 主动取消 | 在可观察的等待点发出受支持的取消操作 | 取消发生在声明阶段；当前执行结束且不继续发起下一步业务操作；会话中的结束原因与实际操作符合预期；工具调用情况、查询结果及连接均已核查 |

M1-S1 的初始脚本可研究 `tool_call_success` 与 `success` 的组合；M1-S2 可研究 `partial_disconnect`；M1-S3 可研究 `stall` 配合控制端取消。这些名称来自当前模拟服务文档，是实验设计起点，不是已经验证通过的配置，也不发布为现成运行命令。

主动取消是控制端操作，不能用“服务端自己断开”代替。以请求已接收、工具已进入或其他可观察事件作为同步点，避免只等固定毫秒后取消。测试必须区分取消与自然超时，并记录同步点和触发证据。

断流是否重试、重试多少次、部分输出如何记录，先依据目标配置和源码确定，再写出明确预期；不能把成功与失败都当作通过。若允许重试，核查最终成功和请求次数；若选择终止，核查明确的失败结果与原因。

三组必测场景以只读工单查询为起点，不要求第一章同时实现完整写操作补偿。后续确认写入、幂等与未知结果在相应业务章节继续验证；取消不能撤销已经发生的外部副作用这一限制仍须解释。

### 离线与无真实凭据的验收证据

环境准备可以单独使用网络。实验执行时允许必要的本机回环通信，阻断外部网络，并记录隔离方式及有效性验证。没有访问外网不等于证明不能访问外网；只有隔离确实生效，才能标注离线通过。隔离措施应限于实验所需范围，不修改整机网络或影响其他运行任务。

使用隔离的实验 home 与明确的测试凭据；确认运行链路不会读取真实提供者密钥或用户现有会话。不得通过打印凭据来证明这一点，也不需要更改用户全局配置。

每组场景保存代码和实验版本、平台、输入与配置、隔离证据、同步点、请求和工具观察、会话结果、外部状态核查、断言结果、进程退出状态与清理报告。清理在成功、失败、取消时都执行；只处理实验拥有的资源，不能为了关闭端口终止其他任务。

记录模拟服务、应用及业务服务各自的生命周期。进程退出为 0 只说明该进程成功退出，不能单独证明断言或取消语义正确。测试驱动器只有全部断言通过才报告场景通过；未清理或结果未知的场景记为未完成。

### M1 分开报告工程通过与读者通过

M1-E 为工程验收：完整样章、可运行改动、图源与实际版面检查、三组场景在隔离条件下通过、原始证据与清理结果齐全。只完成帮助命令、模拟服务启动或文笔试写，不满足 M1-E。

M1-R 为读者验收：初学者按照指定前置知识与样章独立完成正常场景、解释源码与图，并完成迁移练习；记录卡点、求助与返修。若尚无真实读者，保留 M1-R 待完成状态。

M1 只有两部分都通过才进入 M2 的批量扩写。工程先通过但读者尚未验收时，可以继续修正样章与实验，不宣称教学方法已验证或完整 M1 已完成。

| M3 扩写 | 十篇、综合项目与迁移练习 | 分篇验收与覆盖差距可追踪 |
| M4 审校发布 | Markdown、阅读版与 PDF | 引用、实验、版式和版本范围核实 |

排期同时计算研究、设施开发、写作、实验、试读与返修，不以模型生成文字的速度估算完成时间。没有真实试读者时，准确标记“作者自测通过，读者验收待完成”。

## 十、审校与读者验收

### 10.1 每章先检验理解，再检验迁移

读者先复述机制，再运行实验，然后独立修改一个条件，最后处理一个不同于正文例子的需求。迁移练习需要说明选择和验证方法，避免只替换名称即可通过。

对兴趣的观察包括读者是否愿意继续、在哪一段停下来以及原因。对理解的观察包括陌生术语、回翻位置、解释能力和求助次数。不能为了让反馈好看而替试读者完成步骤。

### 10.2 技术、图解与编辑审校

技术审校检查行为、类型、资源、数据、权限、失败与验证；图解审校检查关系、简化、证据和实际可读性；编辑审校检查读者起点、段落连接、术语、例子、节奏和重复。需要删减时，先保留关键保证与失败条件，再调整表达。

源码引用、文档链接、代码块、实验清单和术语可以自动检查。符号存在不等于使用正确，代码编译不等于运行符合业务，自动检查之后仍需对应的实验与人工审核。

### 10.3 章节完成条件

- 本章问题已经回答，读者能明确说出学会了什么。
- 关键图组有依据、图注与解释，图文和实验一致，网页及 PDF 实际版面可读。
- 前置知识有入口，代码与数据有坐标，新增术语有解释。
- 操作说明在声明的平台与基线运行验证。
- 相关失败、取消或恢复有明确结果与处理责任。
- 设计动机有依据，推断有标记，外部结果经过核查。
- 试读状态如实记录，已知问题不会被“已完成”掩盖。

### 10.4 每章呈现验证结论与学生对照

每章设置“本章验证与自检”，在结果揭示前让学生作出预测，运行后对照教材作者实测与自己的结果，并解释差异。记录检查项目、运行条件、预测、实测证据、学生结果、通过条件和未确认范围，不能只有一句“测试通过”。具体使用[章节模板](deepseek-harness-chapter-template.md)。

作者实测、学生复现与第三方报告分别标记。理论章节采用可核查的演算和理解检查；运行章节提供实际输入输出、行为断言、退出状态和清理摘要。网页与 PDF 都保留比较结果所需材料，完整工程日志另附可追踪入口。

一次任务可能包含不同用途的模型请求。模拟服务请求总数、主 Agent 请求数、重试和其他插件请求分别核查；未经核对不能把额外请求直接算作主循环。严格场景按明确请求顺序和断言编排脚本，序列意外耗尽或存在无法解释的额外请求时不报告完整通过。`--repeat-last` 可用于明确的开放式演示，但不能作为隐藏意外请求的通用修复。

按目标区分进程成功退出、主任务完成和全部必验检查通过。可选功能失败即使不使主任务失败，也必须说明发生了什么、影响什么；不能把退出 0 当作没有任何错误的证据。已发生的探针异常先登记并核查，不用未经确认的原因补齐结论。

结果不一致时给出具体排查顺序及证据位置；关键差异未解释时保留未完成状态。章末说明已经掌握的能力、仍未覆盖的条件，以及进入下一章需要通过的检查。模板帮助比较，正文仍用自然语言解释因果。

## 十一、资料组织与版本维护

建议将正文、参考、实验和验证记录分开组织，并通过稳定 ID 相互链接。先在当前 `artifacts/` 中维护规划；新建独立教材仓库、迁移文件、公开发布或改变源码仓库结构另行确定，不由本规划自动触发。

每次升级书稿先比较代码与依赖变化，再定位受影响章节、实验、模块和扩展点。旧书稿保留适用提交，新版说明验证范围；关键机制变化时及时更新，不只等待固定季度。

仓库统计按 M0 要求交付脚本、范围、排除项、提交与原始输出，并与用户提供的历史参考值核对。当前尚未复跑，不把待核对数字作为已验证分母；M0 完成后由其报告提供本教材的范围锚点。

正式进入仓库文档体系时遵循所属目录的文档规范、语言配对与验证要求。书中的讲解链接权威资料，不复制维护完整 API 清单；独立出版保留来源与第三方许可说明。

规划评审、不同版本方案与讨论记录只保留在内部规划历史中，不作为正式教材当前行为的权威资料。发布前检查正文和参考资料的引用，将当前行为指向源码、测试及维护中的权威文档；确有必要的历史取舍另标历史性质与适用范围。

## 十二、首批交付清单

第一批交付分为 M0 与 M1 两批：M0 包含详细目录与学习依赖图、三清单骨架及首批机制清单、精读范围初稿、统计脚本与报告、预算校准和图表清单；M1 包含两章完整图文样章、源码坐标、可运行改动、三组场景证据、试读与返修记录。样章有任务概览、实际交互时序和状态或数据变化图，附图源与网页及 PDF 的视觉检查记录。

样章一选择“一句请求发出去以后”，检验零基础读者是否能从观察建立整体认识。样章二选择“第一个业务工具”，按闭环样章表完整交付；前置基础与环境准备不能代替真实源码、可运行改动与实际断言。

样章二提前试写不代表学生阅读时可以跳过基础。样章验证后再调整正文顺序、章节规模、语言细节与预算，形成可持续执行的写作计划。
