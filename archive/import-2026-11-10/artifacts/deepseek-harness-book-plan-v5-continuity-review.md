# DeepSeek Harness 教学书 V5：学习连续性自检

日期：2026-11-10。

范围：[V5 编写方案](deepseek-harness-book-plan-v5.md)的教学顺序、知识依赖、章节衔接与学习验收。本报告不修改 V5，也不将建议目录视为已经完成的教材。

## 自检结论

V5 已有较完整的源码、图解、实验和交付要求，但尚不足以证明整本书能持续带领零基础学生学习。它说明了每个部分应该讲什么，却没有逐章落实学生凭什么能读懂下一部分。

最需要调整的是内容组织：让一个已经能运行的小程序逐步遇到新需求，让新知识解决刚出现的问题，再把结果留给下一章继续使用。每个小节都需要检查理解，每个阶段都需要减少提示，最终验证学生能否读懂未讲过的专业实现。

你提到的一周学习经历，提供的是教学效果参照，不构成本书的统一学习周期。质量应以真实学习过程和独立能力检验。

## 一、怎样理解这个参照

清华大学出版社对王爽《汇编语言》第四版的介绍，强调知识细分、渐进的学习线索与关键机制分析；其公开目录也展示了由基础到寄存器、内存访问，再配合实验深入的组织方式。这是本次理解教学参照的资料依据。[出版社图书页面](https://www.tup.tsinghua.edu.cn/bookscenter/book_07970801.html)

本报告没有通读或核对该书全部章节，也不把下列具体做法归为该书原文。以下是结合你的学习经历与当前项目提出的教学设计建议。

你期待的效果包含四件事：阅读时知道为什么需要新知识，学习时不必反复猜测尚未解释的前提，动手后能发现自己确实多会了一件事，学到后面能独立分析陌生代码。

因此，本书既要使单章通俗，也要维持整本书的知识连续性。一个介绍得很清楚的章节，如果依赖学生尚未掌握的概念，仍然可能成为学习障碍。

## 二、V5 的具体不足

以下区分“方案尚未落实的要求”和“需要试读验证的风险”。没有学生试读证据，不能声称某个章节必然让学生学不会。

| 问题 | V5 中的依据 | 对学习的影响 | 建议修正 |
| --- | --- | --- | --- |
| 框架讲解早于充分的使用经验 | 第二篇集中讲 Context、Service、事件模式、释放与重载，第三篇再讲多种应用组合 | 学生可能记住术语，却不清楚为什么需要这些机制 | 先完成一个受支持的最小工具扩展，再因需求逐步深入框架 |
| 基础知识仍然压得较密 | 第一篇一个候选章节同时承担异步、错误、取消和测试 | 不同难度的概念可能同时成为障碍 | 拆成小节与检查点，取消与并发在任务确实会等待时展开 |
| F8 的引入时间偏晚 | 网络基础安排在协议与客户端前，但前面实验已经使用本地模型服务 | 入门操作可能依赖学生不懂的地址、端口和请求概念 | 最早使用前解释本地服务与地址，协议细节随后深入 |
| 章间交接缺少具体约定 | 已有主线案例和篇末成果，未逐章列出输入产物、输出产物与知识前提 | 同一案例名称不能保证实现与理解连续 | 每章明确承接哪个可运行版本、解决什么限制、留下什么成果 |
| 数据进阶仍有跳跃风险 | 第五篇先进入格式迁移，再讲重新附着等恢复问题 | 学生可能尚未经历普通重启，就先面对历史兼容性 | 先保存与读回，再推导视图和恢复，最后解释版本迁移 |
| 检查粒度主要停在章节与阶段 | M1 工程及读者验收较完整，缺少小节理解检查安排 | 学生可能带着早期误解完成整章操作 | 在依赖点之前增加预测、解释与小改动检查，并提供补救路径 |
| 独立阅读训练不够明确 | 能力目标要求阅读源码，实验仍较多依赖给定入口和完整步骤 | 能跟随示例，不一定能处理陌生代码 | 按阶段撤去提示，增加未讲解过的同类模块迁移阅读 |
| 工程证据与学生正文未充分分开 | 样章要验证隔离、断流、取消、记录与清理，要求合理但密集 | 可能为了证明样章可靠，让初学者一次承担全部验证机制 | 作者端完成全部工程验证，学生按前置知识逐步学习，进阶场景明确依赖 |
| 缺少连续章节试读 | M1 重点验证两篇选题，二者不必相邻 | 可以证明单章质量，尚不能证明承上启下 | 增加一个连续三章的小段学习路径，用同一学生和同一项目验证 |

这次调整不需要削弱技术要求。需要改变的是这些内容首次出现的时机，以及学生要在每一步承担多少新知识。

## 三、建议采用的连续学习路线

### 3.1 先形成一条真正能走完的主线

主线建议从已有系统的观察进入，从一个小的业务函数开始动手，再形成真实工具扩展。学生积累了使用经验后，依次理解模型请求、工具循环、事件状态、等待与取消、持久化和框架组合。

底层机制仍然深入讲，但不要求学生第一次接触系统就先掌握底层所有概念。最终通过源码阅读和独立实现补齐机制理解，初次使用的简化部分必须明确回访。

| 学习阶段 | 承接的已有能力 | 当前遇到的问题 | 本阶段新增知识 | 完成后留下的东西 |
| --- | --- | --- | --- | --- |
| P1 观察任务 | 会操作准备好的示例 | 一条输入后，模型和程序分别做了什么 | 最小角色划分、输入与输出 | 任务观察表与概览图 |
| P2 写查询函数 | 能观察查询结果 | 怎样让程序按编号返回正确工单 | 变量、对象、函数、分支、最小断言 | 能独立测试的本地查询函数 |
| P3 接入真实工具 | 能解释查询函数 | 怎样把这个函数交给现有系统使用 | 最小插件与工具声明、参数、结果、profile 入口 | 能运行的只读工具及接入图 |
| P4 理解请求与循环 | 已完成一次真实工具任务 | 工具结果怎样帮助生成后续答复 | 消息、请求、最小事件、turn 与 step | 对同一任务的时序、记录与源码说明 |
| P5 等待与取消 | 能解释正常顺序 | 查询没有立即返回时，系统怎样继续或停止 | Promise、等待、错误传播、取消与同步点 | 可控制的慢查询与取消实验 |
| P6 保存与重新进入 | 能观察内存中的任务状态 | 关闭应用后，还能知道发生了什么吗 | 保存、读回、投影、重启与状态归属 | 可核查的持久任务记录 |
| P7 理解并替换框架能力 | 已使用插件、工具和记录 | 换数据源、卸载插件时怎样保持行为清晰 | Context、服务三角色、事件模式、资源依赖与释放 | 一个可替换提供者与生命周期说明 |
| P8 控制业务写操作 | 能控制与核查只读任务 | 怎样确认写入，如何处理重复或未知结果 | 权限、审批、幂等、结果核查 | 可控的业务修改流程 |
| P9 协作与外部入口 | 已有稳定单任务应用 | 怎样让其他程序、多个 Agent 与用户参与 | SDK、协作、协议与界面状态 | 可操作的协作应用 |
| P10 独立研究与交付 | 能开发和追踪主线应用 | 面对陌生模块与新业务，怎样自行判断 | 不提示入口的阅读、方案比较、综合验证 | 陌生模块分析与业务交付 |

P1–P10 是教学顺序建议，不是对真实运行时的逐层分解。机制可以在多个阶段回访，但每次回访需要增加新的理解或能力。

### 3.2 保留内容范围，重新安排第一次出现的位置

V5 的十篇可以继续承担内容归属与查阅索引，主线顺序需要据此重排。学生不应为了完成一次基本工具接入，提前遍历 HMR、所有事件模式和所有 profile。

早期模板要说明哪些配置已经准备、为什么可以暂时沿用、当前实验不会修改哪些部分，以及将在哪个阶段回访。遇到不理解的现象时提供可追踪入口。不能靠“先这样写”永久掩盖关键机制。

教学用独立最小实现先在理解正常循环后完成，再随着取消、持久化等阶段逐次补充。正式应用实验始终采用受支持的 `dsh` profile，不因教学简化引入额外的正式启动方式。

### 3.3 正式实现与教学实现分开标记

读者在每个例子中都应该知道自己正在运行本地函数、正式插件组合，还是独立教学实现。三者的名称、限制和启动方式分别说明。

教学实现必须忠实解释机制，不能先建立与正式实现相反的规则，再要求学生在后文推翻。简化掉的并发、生命周期或数据约束列在可回访清单中，后续逐项解决。

## 四、每章需要交给下一章什么

每章编写前填写以下交接表，M0 审核后才能进入连续正文试写。

| 项目 | 要记录的内容 |
| --- | --- |
| 学生进入状态 | 已能独立完成的操作及对应前置检查 |
| 输入产物 | 上一章的代码、数据、配置、图与实验版本 |
| 新问题 | 上一章方案在什么具体需求下不够用 |
| 新增知识 | 解决当前问题所需的最小概念集合 |
| 暂不展开 | 本章沿用的机制、适用限制与明确回访位置 |
| 输出产物 | 本章可运行结果、修改内容与解释材料 |
| 检查与补救 | 学生需要回答或操作什么；失败后回到哪一小节 |
| 下一章入口 | 本章成果将支持什么进一步需求 |

新增术语、操作和代码接口建立首次教学位置及后续使用位置。后文首次依赖某项知识时，必须能追到前面的解释和检查；只在截图、配置或注释里出现过，不算已经教过。

相邻章节共用一条演进代码线，每章有可重跑快照、变更说明和累计回归。学生可从自己的版本继续，也可从已核实的章节起点恢复。快照编号表示教材实验版本，不混同于仓库会话格式版本。

图也随内容演进。相同参与者保持一致命名，新增关系局部突出，同时保留独立可读的完整图。章末让学生解释新增部分与前一章有什么关系。

## 五、连续三章的教学设计示例

下面展示 P2–P4 的衔接方式。它是设计演示，没有声称这些代码或场景已经实现、运行或试读。

### 章 A：让程序查到一张工单

进入时，学生已经看过准备好的任务演示，知道输入编号后会得到结果，但还不会自己提供这项能力。

本章使用少量固定工单数据讲函数、参数和返回值。先让学生预测查找结果，再测试存在、不存在的编号。错误处理与未知结果只讲当前例子需要的部分，不同时展开网络和 Agent 生命周期。

完成时，学生有一个可以直接调用和测试的查询函数，并能说明它读了哪些数据。函数本身不依赖模型；这一点通过独立运行确认。

章末承接：“查询函数已经能按编号返回结果。接下来，我们把它接入刚才使用的系统，检查模型请求查询时，程序能否正确调用它。”

### 章 B：让系统调用你的查询函数

开篇拿出上一章的函数与测试结果。先解释工具声明为什么需要名称、输入和结果，再逐步完成真实工具接入。模板只准备当前不需要修改的启动部分，关键注册、参数处理和函数调用全部讲清。

真实源码阅读沿着少量关键位置进行：声明在哪里、谁注册它、执行时怎样进入业务函数。更深的注册表与框架释放机制标记回访位置，不在本章一次展开全部实现。

实验使用可控模型响应，核查实际参数、函数调用次数和工具结果。正常调用失败时，提供参数、注册、配置三类定点排错，帮助学生利用已学知识查原因。

章末承接：“工具确实执行了查询。可是，查询函数返回的是工单数据，界面显示的却是一段完整答复。我们还需要找到这两者之间的那一次请求。”

### 章 C：工具结果怎样进入下一次请求

使用同一任务、同一工具与数据，先让学生预测请求次数，再观察实际请求和事件记录。逐步标出输入、工具调用、工具结果、后续请求和答复，建立最小消息与循环知识。

源码精读集中在这个正常流程所需的路径，并把图上的序号与代码及观察记录对应。此时解释 turn 与 step，因为学生已经见过需要区分它们的实际过程。

随后只改变工单状态，让学生预测后续请求和结果会在哪里变化，并核查实际数据。若测试只改脚本答复却没有使用真实工具结果，也应被独立断言发现。

章末承接：“现在我们能解释一次顺利完成的任务。下一次查询会故意晚一些返回。我们先观察程序在等待时做什么，再决定应该怎样停止它。”

### 这一段连续教学怎样验收

学生需要从章 A 的成果完成章 B，再从章 B 的运行结果进入章 C。每次主要增加一类任务，已有函数、工具名称和数据保持连续。

章 B 后插入章 C 不增加新的业务背景。等待、取消与断流的工程验证仍由作者完成，但学生端按理解顺序进入后续排错实验，避免把全部复杂性集中在首次接入工具的正文里。

## 六、小节检查与独立阅读训练

### 6.1 检查放在知识将被依赖之前

介绍返回值之后检查学生是否能区分返回结果和屏幕输出；介绍异步之后检查是否知道下一行何时执行；介绍取消之后检查是否知道已经发生的外部修改是否会撤销。

每项检查给出可判断的答案依据与补救入口。正常主线需要的前置未掌握时，推荐先完成补救再进入依赖内容；与当前主线无关的进阶练习可以稍后返回，不把所有扩展题都变成前进障碍。

检查题不靠死记名词。采用预测结果、补一处操作、指出数据来源、解释错误或画出路径等形式。提示和答案放在作答之后，解释错误原因，不能只有结论。

### 6.2 同一知识逐次加深

| 知识 | 首次接触 | 后续加深 | 独立运用 |
| --- | --- | --- | --- |
| 工具 | 让查询函数可被调用 | 读注册、执行管线、作用域与释放 | 接入未演示过的工具并验证 |
| 会话 | 看到任务留下的事件 | 解释投影、持久化与模型历史 | 判断新业务需要怎样记录 |
| 取消 | 停止一个可控等待 | 跟踪传播、资源结束与未知结果 | 分析一个陌生长任务的取消风险 |
| 插件 | 挂接一项业务能力 | 理解 Context、事件、服务与生命周期 | 替换提供者并判断影响 |

回访时明确说明上次解决了什么、现在增加什么。不能重复入门定义却不增加能力，也不能以“之前见过”省略尚未教过的推理。

### 6.3 逐步减少提示

第一次源码阅读提供完整入口和解释；下一次只给模块范围，让学生寻找符号；再后面给业务现象，让学生定位实现、提出预测并验证。

毕业练习应包含一个书中未逐段解释过的模块。学生提交入口、关键类型、调用或事件关系、数据归属、失败处理、一次运行验证与尚未确认的内容。作者核对证据，不能只看报告措辞是否专业。

通过这项练习，才能更接近你描述的学习效果：离开示例后，仍能读懂专业实现并据此设计程序。

## 七、怎样验证章节真的连贯

### 7.1 连续三章试读

从一个明确起点开始，由同一名初学者连续完成三章。记录每章进入时的知识与代码、陌生术语、回翻位置、求助点、完成结果，以及进入下一章时是否能继续使用自己的成果。

学生自行学会之后可以使用章起点快照排除偶发环境问题，但必须记录切换原因。教师代写、替学生定位后才通过的内容，不能当作独立完成。

单名读者提供初步证据，不代表所有人都能顺利学习。反馈不同应检查基础、环境、表述和步骤，再确定修订或适用范围。

### 7.2 两种检查同时进行

知识检查追踪每个新增概念何时解释、何时练习、何时被依赖；实现检查从上一章的输出继续应用下一章变更，执行累计回归。工具只能帮助发现缺失引用与运行失败，不能自动判断叙述是否自然。

编辑再进行一次连续阅读，不按单章拆开：检查新问题是否从上文产生，例子与角色有没有突然变化，学生是否需要未声明的新工具或资料，以及结尾是否真的完成当前承诺。

### 7.3 发现断点时怎样修复

先判断是前置未教、解释不清、概念密度过高、代码版本断裂还是实验环境问题。然后选择补解释、拆小节、调整顺序、增加检查或修复配套材料。

优先修正当前断点。不能靠补一句“下一章会详细解释”长期推迟当前操作必须理解的知识，也不能用更多术语和配图掩盖缺失的推理。

## 八、对现有交付标准的修订建议

| 阶段 | 保留 V5 的要求 | 建议新增 |
| --- | --- | --- |
| M0 | 机制清单、精读范围、统计脚本、预算校准 | 主学习路线、知识首次出现与依赖表、相邻章交接表、简化机制回访清单 |
| M1-E | 两章闭环样章、图源、三组工程实验与清理证据 | 单章采用验证结论与学生对照；连续片段不作为第一篇样章的前置条件 |
| M1-R | 独立操作、解释、迁移及返修记录 | 先验证闭环样章的单章学习；连续三章另列后续验收 |
| M1 完成后、M2 批量扩写前 | 已通过的样章与工程证据 | 连续三章试读、逐章变更、累计回归和知识跳跃记录通过 |
| M2 | 可完成的首轮学习路线 | 依赖检查通过，前章产物能进入后章，后章不隐含引入必需前提 |
| M3–M4 | 全面扩写、覆盖与发布验收 | 持续回访旧知识，逐步减少提示，陌生模块阅读与独立业务设计验收 |

连续三章可以复用已完成的样章，另补必要相邻章节；若无法形成连续片段，另选一段试写。先产出第一篇真实闭环样章，再验证连续性，不把三章同时完成设为开始写样章的条件。原定样章工程验证不减少，新增片段也不要求每章重复整套故障实验。

作者用的编写、统计和验证规范，与学生阅读的正文分别组织。正文呈现理解所需证据，完整工程记录在配套资料中可追溯。书的篇幅预算需要在主线重排后重新校准，不因预算已经列好就保留学习断点。

本次自检后的判断是：V5 可以继续作为工程与内容范围基线，但连续教学的设计还需要以上补充及实际试读。现阶段不能宣称已经达到你期待的教学水平。

### 8.1 学习重排后保留业务交付主线

P8–P10 仍以企业问题处理助手为连续业务成果，并关联原有三个综合项目，不能仅以三个阶段名称代替完整设计。P8 承接项目一，完成项目二的确认写入、权限、重复请求与未知结果；P9 完成项目二的协作并进入项目三的 SDK 与交互；P10 完成项目三的运行、部署、故障核查和升级。

业务追踪表为每项需求记录角色、数据归属、授权检查、执行、记录、交互、验证与所属项目。多租户作为进阶业务需求单列，检查身份、租户数据与执行资源的隔离；实际支持与待开发内容先核实，不以已有通用审批或沙箱等同完整多租户隔离。
