## 摘要

一本好的源码书，应该让读者越来越敢于打开真实代码。最初，他只能看到界面上出现了一段回答；后来，他能沿着请求找到循环、工具和事件；再后来，他能判断一个业务需求应该改哪里，解释自己的设计，并用测试确认它确实有效。

这本书以 DeepSeek Harness 为研究对象，从零基础出发，带读者走完这段过程。正文用具体任务串起原理，源码精读解释关键机制，实验把理解变成能力，模块索引承接全仓库查阅。书中的每一次深入，都应当回答读者已经产生的疑问。

全书以中文写作，技术术语首次出现时说明原名。阅读体验、技术准确性和独立开发能力共同决定内容是否合格。

## 一、读者最终要获得什么

### 1.1 从看见结果，到解释结果

读者不需要带着框架开发经验开始学习。书中先帮助他观察一次任务，再解释程序、模块、异步执行和事件等基础知识，逐步进入框架内部。

学完后，读者应能沿着一次用户操作说明：应用怎样启动，输入怎样进入 Agent，模型收到哪些内容，工具怎样执行，状态怎样记录，界面怎样更新，以及失败后由谁处理。他还应能据此增加业务能力，并对自己的修改提供验证证据。

### 1.2 能力目标

| 能力 | 达成表现 | 验收材料 |
| --- | --- | --- |
| 能解释 | 用自己的语言说明模型、Agent、工具、循环与会话的关系 | 一份任务流程讲解，能回答后续追问 |
| 能追踪 | 从用户入口找到类型、实现、消费者、记录和显示 | 带源码坐标的流程图与观察记录 |
| 能修改 | 判断变更影响并完成一个明确功能 | 修改、相关测试与兼容性说明 |
| 能扩展 | 为业务选择工具、服务、配置、协议或客户端扩展方式 | 可运行的业务功能及设计说明 |
| 能构建 | 独立实现教学用最小 Harness，解释与正式实现的差异 | 最小实现、演示与差异清单 |
| 能交付 | 处理权限、取消、重复执行、未知结果、恢复与升级 | 综合项目、故障验证与运行手册 |

能力分级采用“能讲清 → 能改 → 能造 → 能评”。阅读完章节不自动等于掌握，需要经过操作、解释和迁移练习。

### 1.3 全仓库覆盖的范围

所有模块都有定位、职责、依赖和阅读入口；关键机制深入到实现与失败路径；相似提供者说明共同接口与差异。应用、SDK、原生能力、构建与测试设施也进入范围清单。

实验性模块保留完整定位，按研究价值选择深入程度；第三方与 vendored 实现讲清本项目依赖的机制，精读其中影响框架理解的部分。模型训练与推理算法的完整实现不属于本书范围。

覆盖清单必须区分“建立索引”和“完成讲解”。只有清单、章节与验证相互对应，才报告覆盖完成情况。全书不以逐行转述作为完成标准。

## 二、整本书怎样讲才好读

### 2.1 让读者先在意这个问题

每章从一个具体、可理解的场景开始。读者应知道事情发生在哪里、谁遇到困难、为什么值得解决。背景只保留理解问题需要的部分，不虚构事故、测量结果或作者经历。

讲工具执行，可以先让企业助手查询一张工单；讲取消，可以让查询正在等待远端返回；讲恢复，可以观察应用重新启动后哪些信息还在。先建立需要，再介绍机制名称。

### 2.2 用连续的发现维持阅读兴趣

章节的基本推进是“看到现象 → 作出预测 → 运行观察 → 解释原因 → 对照源码 → 尝试改变”。每次只提出当前最值得解决的问题，回答后再进入下一层。

读者的错误预测也有价值。例如，他可能以为按下停止就能撤回已经发出的业务请求。实验应帮助他分清本地取消、远端执行与结果确认，而不是把错误答案写成用来衬托作者的笑话。

段落之间需要有因果联系：上一段指出的问题，由下一段的方法解决。避免在叙述中连续插入互不相关的定义，也避免每一小节都用同一种设问开头。

### 2.3 用成熟、自然的中文解释技术

- 以读者为交流对象，适度使用“你”和“我们”，避免机械地重复。
- 先说明作用，再给名称；抽象概念后紧跟小例子，关键术语前后一致。
- 一段推进一个主要意思，长短句交替，让解释有停顿，也能连续读下去。
- 原理与过程用连贯文字讲清；比较用表格；步骤用编号；图只承担文字难以表达的关系。
- 代码标识保留原名，解释使用准确中文；不用中文译名取代读者实际需要搜索的符号。
- 直接说明行为、条件、责任与结果。避免“显然”“很简单”“一看就懂”等给初学者施压的词。
- 不用“魔法”“黑科技”“颠覆”等词制造兴奋，不以人格化故事或夸张比喻替代机制。
- 不使用反复对立的句式、成串口号、每段加粗结论或频繁感叹来催促读者。

技术准确性优先。不能为了流畅删去取消条件、异常路径、数据归属和兼容性限制；应调整讲述顺序、增加例子，让这些内容变得可理解。

### 2.4 给阅读节奏留出变化

一章可以从操作开始，也可以从一段短日志、一张状态图或一个业务需求开始。八项教学内容都需要覆盖，但不要求每章机械使用相同的八个小标题。

代码每次只展示当前解释需要的连续片段，交代输入、输出、所在位置和调用者。完整实现保留稳定链接。读者完成预测、修改或解释后，再给答案，避免正文替他完成全部思考。

高级内容放在明确标注的进阶阅读或参考页中，主线只引入当前需要的知识。所谓循序渐进，包括让读者知道哪些细节暂时可以放下，以及何时会回来理解。

### 2.5 一章需要完成的承诺

章节开头说明读者将解决什么问题；正文兑现这个承诺；结尾用简短的实验结果与解释检验理解。当前问题必须得到回答，延伸阅读不能替代答案。

下一章从本章真实留下的限制继续。例如，工具已经能执行，但如果应用退出后任务记录消失，就自然需要学习持久化。这样的衔接比“接下来更精彩”更能让读者愿意继续。

### 2.6 把风格变成可检查的要求

| 检查点 | 合格表现 |
| --- | --- |
| 开篇 | 不熟悉源码的人也知道场景、困难与本章目标 |
| 术语 | 首次使用有解释，读者不需要猜缩写 |
| 连贯 | 能说出相邻两节为什么按这个顺序出现 |
| 实现 | 能把代码片段对应到前面的问题，而不只是复述语句 |
| 取舍 | 说明收益、成本与适用条件，有依据或明确标为分析 |
| 结尾 | 当前问题已解决，下一步学习有实际理由 |
| 试读 | 读者愿意继续，且能复述与独立完成任务 |

“欲罢不能”是阅读体验目标，不能由作者自评保证。试读同时观察兴趣、理解和独立操作，不能只问读者是否觉得文笔好。

## 三、语言风格试写

以下两段用于展示正文语气。场景为教学设定，没有声称已经运行对应实验；正式样章需要补上基线、输入、源码坐标与运行证据。

### 3.1 开篇试写：一句请求发出去以后

假设你第一次打开这个项目，想让它帮忙查一张工单。你输入：“看看 1042 号工单为什么还没处理。”界面开始出现文字，接着显示一次工具调用，最后给出答复。

从使用者的角度看，这件事很自然：提出问题，等待答案。但如果现在要你加一个功能——在答复之前，把处理建议交给负责人确认——你会把代码写在哪里？

直接修改模型请求似乎可行，可负责人可能过十分钟才回复。修改工具也有道理，但并不是每次查询都需要确认。再考虑一步：等待期间关闭应用，重新打开后，这次确认还在吗？

一个小需求，把模型、工具、等待状态和数据保存联系到了一起。要把它做好，我们需要知道这几个部分怎样配合。

现在先不用记住包名，也不用打开最长的那个文件。第一件事，是把刚才的任务再看一遍。这次我们留意三个问题：什么时候向模型发送了请求，什么时候真正执行了查询，查询结果又怎样进入下一次请求。

在配套实验里，你会先使用准备好的响应脚本运行这个过程。它让我们控制返回内容，逐步观察每个环节。等你能指出模型负责哪一步、程序负责哪一步，再打开源码，就会知道自己正在寻找什么。

这一章结束时，你不需要解释整个仓库。但你应该能够画出这次任务经过的几个主要环节。那张图会在后面的章节里越来越具体。

### 3.2 原理试写：按下停止之后，什么停下了

企业助手正在提交一项业务变更，你忽然发现选错了工单，于是按下停止。界面不再显示新的内容。

工单有没有被修改？仅凭界面停下来，还不能回答。

请求可能尚未离开本机，也可能已经到达业务系统。甚至业务系统已经完成修改，只是响应还在返回途中。如果这时直接重试，你可能提交第二次；如果直接显示“已取消”，又可能让使用者误以为业务没有变化。

因此，我们需要分别确认两件事：当前执行是否停止，以及远端操作的结果是否已知。前者属于执行控制；后者需要业务系统提供可以核查的依据。

这一节的实验会使用可重置的本地业务服务，分别安排“提交之前取消”和“提交之后尚未收到响应”两种情况。你要先预测工单状态，再从服务端读取实际结果。之后，我们才沿着源码检查取消信号如何传播，以及未知结果如何被表达。

当你能解释这两个结果为什么不同，就已经开始具备业务开发需要的判断力。下一步，是设计一个即使收到重复请求也能识别同一次操作的业务接口。

## 四、学习路线与基础准备

### 4.1 先体验，再由底层深入

主路线为：一次完整体验 → 基础准备 → Cordis → 启动组合 → 最小会话知识 → Agent 循环 → 数据进阶 → 能力扩展 → 协作 → 协议与交互 → 业务交付。

开篇体验使用准备好的环境和脚本，允许读者暂时只会操作。随后需要独立安装、阅读和修改时，再补齐相关知识。基础单元是正文的一部分，不把零基础读者引向一串没有讲解的外部链接。

### 4.2 基础单元及进入条件

| 单元 | 学习内容 | 需要独立完成的操作 | 后续用途 |
| --- | --- | --- | --- |
| F1 程序如何运行 | 命令、路径、工作目录、文件和进程 | 找到输出与错误，区分相对路径和绝对路径 | 环境准备与启动 |
| F2 数据与函数 | 变量、对象、数组、函数、返回值 | 写一个工单查询与格式化函数 | 阅读模块 |
| F3 类型与分支 | 类型、接口、联合类型、收窄 | 处理成功、失败和未知结果三种情况 | 服务、事件与协议 |
| F4 模块与依赖 | ESM、导入导出、包与工作区 | 拆分并连接两个模块 | 插件与工程布局 |
| F5 异步执行 | Promise、async/await、顺序与并发 | 等待结果并解释执行顺序 | 模型、工具与 RPC |
| F6 错误与取消 | 异常传播、finally、取消信号、清理 | 中止等待并验证资源释放 | 生命周期与恢复 |
| F7 测试与调试 | 断言、断点、日志、失败定位 | 先观察失败，再修正并解释原因 | 实验验证与二次开发 |
| F8 网络与界面基础 | 请求响应、流、状态、渲染 | 追踪一次本地请求与界面变化 | 协议与客户端 |

F1–F7 分阶段穿插在第一篇中，F8 在协议与客户端前补充。各章列出基础单元依赖及补学入口；已具备基础的读者可通过练习跳过讲解。

### 4.3 三条阅读路径

学生路径按主线学习并完成基础练习；工程师路径通过基础自测后进入框架与循环；业务查阅路径从需求选择扩展点，再返回对应机制和实验。三条路径共享数据与生命周期知识，不能只学工具注册就直接承担业务写操作。

阅读时长在试读后按学习、实验、排错和项目四类投入估算，不承诺固定周数。章节数量也不代替难度评估。

## 五、全书候选目录

以下为可调整的篇章目录。篇号表示教学组织，未声称仓库存在同名分层。正式章号在学习依赖与样章验证后确定。

### 第一篇：从一张工单开始

1. 一句请求发出去以后：观察完整任务，区分模型、工具和 Harness。
2. 第一次自己运行：路径、进程、开发环境与准备检查。
3. 把数据交给函数：用工单小程序学习变量、对象和函数。
4. 让代码可以组合：类型、模块、包与工作区。
5. 当结果不会立刻返回：异步、错误、取消与测试基础。
6. 打开真实仓库：从需求找到入口，建立第一张源码地图。

出口成果：能运行入门实验，读懂小模块，并解释一次任务的主要环节。

### 第二篇：插件怎样组成一个应用

1. 从增加一个能力开始理解插件。
2. Context 怎样连接插件与服务。
3. 服务定义、提供者与消费者怎样协作。
4. 事件的不同调用方式怎样影响扩展。
5. 插件卸载时，谁负责结束工作和释放资源。
6. 配置校验与重载：哪些失败必须尽早暴露。

出口成果：写出可替换服务和消费插件，验证注册、依赖与释放。

### 第三篇：从启动命令到运行中的插件树

1. 应用从哪里进入，何时算启动完成。
2. profile 怎样保存应用组合，运行时数据存在哪里。
3. bundle 与 patch 怎样叠加和覆盖。
4. Web、headless、SDK、sdk-minimal 与 ACP 怎样选择。
5. 查看实际配置，并定位一项启动故障。

出口成果：使用受支持的 profile 启动方式组装教学应用，说明配置来源。桌面专属组装在第九篇深入。

### 第四篇：一次任务为什么需要一个循环

1. 先认识会话：事件、消息与模型历史的最小知识。
2. Agent 接口与运行中的注册表。
3. turn 与 step：任务怎样进入、继续与结束。
4. 输入认领、队列和插入的新消息。
5. 提示与工具声明怎样进入请求。
6. 工具调用怎样经过执行管线。
7. 模型流式响应、失败重试与取消传播。
8. 亲手构建最小循环，并与正式实现对照。

出口成果：完成综合项目一，追踪请求、工具、记录与取消。最小循环采用内存记录，持久化与重启恢复在第五篇增加。

### 第五篇：程序退出后，什么应该留下

1. 从事件记录解释已经发生的事情。
2. 投影怎样把记录变成可读状态。
3. 持久化提供者、格式识别与版本迁移。
4. 重启、重新附着与中断任务分别怎样处理。
5. 上下文压缩、请求历史与计量。
6. 会话、设置、凭据、附件、工作区与业务数据库的归属。

出口成果：解释状态来源，完成一项投影实验和一个受控恢复实验，核对保存前后的业务与会话状态。

### 第六篇：把工具接到真实业务

1. 一个新需求应该落在工具、服务还是提供者。
2. 文件、工作区与执行环境怎样配合。
3. subprocess、Shell、持久终端与 SSH 的分工。
4. 沙箱与审批怎样约束操作。
5. Web、LSP、MCP 与技能怎样参与任务。
6. 后台任务、调度、目标、待办与计划。
7. 附件、交付物与其他能力家族的查阅方法。
8. 业务写操作：确认、重复请求和未知结果。

出口成果：完成综合项目二的业务执行部分。能力家族是否足够承接全部模块，由覆盖清单检查，不能由目录名称推断。

### 第七篇：让多个 Agent 共同完成任务

1. 子 Agent 怎样创建，谁拥有它的资源。
2. 消息、发现、等待、中断与结果传递。
3. 预算与失败怎样影响父级任务。
4. 团队任务板与工作流分别解决什么问题。
5. preset 怎样形成可复用的业务组合。

出口成果：为综合项目二增加协作，验证等待、中断和父级收敛。不同协作机制的实际保证分别从源码核实。

### 第八篇：从另一个程序驱动 Harness

1. 请求响应、流与进程通信的基础准备。
2. Host、API 与 BFF 的职责。
3. 类型、RPC、网关与流式同步。
4. 断线以后，调用方怎样重新知道状态。
5. TypeScript、Python SDK 与 ACP 的使用与实现。

出口成果：从外部程序驱动会话，追踪输入、状态与结果，说明哪些操作发生在不同进程或网络之间。

### 第九篇：让用户看懂并控制执行

1. 界面状态与渲染的基础准备。
2. 客户端启动与插件激活。
3. 会话视图怎样结合记录与实时更新。
4. 工具卡片、提问与人工确认。
5. 等待、取消、失败、重连与恢复的完整交互。
6. 布局、键盘、焦点、响应式、主题与国际化。
7. 桌面应用的组装、平台依赖与构建。

出口成果：为主线案例完成业务工具卡片与人工交互；平台构建作为有条件的进阶实验单独验收。

### 第十篇：把一个功能做成可维护的应用

1. 从业务需求选择扩展点与数据归属。
2. 将模型判断与确定性业务规则分别实现。
3. 权限、审批、幂等、结果核查与审计。
4. 可观测性、测试与性能验证。
5. 在干净环境运行，处理故障与升级。
6. 研发助手与报表助手：把所学迁移到新需求。

出口成果：完成综合项目三，提交业务应用、验证报告与运行手册。

### 附录与参考册

包含术语、基础练习答案、模块索引、机制与扩展点索引、源码阅读入口、实验说明、故障排查与版本对照。完整 API 清单优先链接已有权威资料；书中提供理解和使用这些资料的方法。

## 六、贯穿案例与三个综合项目

### 6.1 主线：企业问题处理助手

主线从只读查询开始，逐渐加入资料检索、处理建议、人工确认、业务写入、协作、持久记录与界面。工单业务使用可重置的本地模拟服务，避免入门依赖真实企业账号。

业务服务保存工单的权威状态；Harness 组织模型、工具、执行与会话；人工确认表达被确认的具体操作；客户端负责让用户理解状态并采取行动。模型可以提出建议，但业务权限与规则由确定性代码执行。

所有业务能力标记为“已有能力、组合实现或配套新增”。规划中出现需求，不表示仓库已经提供完整实现。

### 6.2 综合项目一：能够解释的最小任务系统

输入是查询工单的请求及可控模型响应。输出是查询结果、执行记录和一份流程解释。读者先使用正式组合观察，再独立实现教学用最小循环。

验收需要覆盖多次模型请求、一次工具调用、无工具的答复与取消；能指出模型请求内容来自哪里，并解释教学实现省略的持久化、并发与权限机制。所需模拟设施与脚本由配套项目实现或复用后验证。

### 6.3 综合项目二：能够控制的业务执行

输入是带权限与确认要求的工单修改任务。输出是可核查的业务状态、确认记录、执行结果与协作报告。

验收包括只读权限拒绝写入、确认与实际操作一致、重复请求识别、取消后的状态核查、响应丢失时表达未知结果，以及子 Agent 失败后父级正确结束或报告。涉及幂等的能力由模拟业务服务与业务插件明确实现，不能假定 Harness 自动提供。

### 6.4 综合项目三：能够交付的业务应用

输入是一份包含业务需求、用户角色和运行条件的项目说明。输出是可运行应用、SDK 或 Web 入口、工具卡片、持久数据、故障验证报告和运行手册。

验收要求另一位读者按手册完成环境准备、运行、正常操作、失败复现、重启核查与版本升级。未取得目标平台或外部服务时，明确列出尚未验证的范围。

### 6.5 迁移练习

研发助手练习终端、LSP 和评审协作；报表助手练习调度、批处理与交付物。读者需要重新划分业务责任并选择扩展点，提交一项与主案例不同的设计理由及验证证据。

## 七、源码研究与覆盖标准

### 7.1 三类清单各自回答一个问题

| 清单 | 主要问题 | 记录内容 |
| --- | --- | --- |
| 模块清单 | 仓库有哪些实现单元 | 路径、包名、职责、依赖、文档、章节与讲解深度 |
| 机制清单 | 一个行为怎样跨模块完成 | 入口、类型、状态、消费者、事件、失败路径与实验 |
| 扩展点清单 | 业务开发者怎样参与或替换行为 | 注册方式、前置条件、生命周期、数据影响、消费者与示例 |

模块清单覆盖应用、包、Python、原生、脚本、测试和相关 vendor 范围。稳定 ID 用于跟踪改名与迁移，不能只靠行号关联。

### 7.2 自动提取与人工审核分工

脚本提取文件路径、包名、显式依赖与文档链接；CodeGraph 提供符号和结构关系；作者审核职责、动态关系、机制解释、章节安排与验证证据。自动结果包含来源和基线，不能把推断字段标为人工核实。

源码坐标使用仓库相对路径、符号名和提交哈希。展示时可以缩写包名；运行时目录与命令单独记录。没有核实的路径不进入教学操作说明。

### 7.3 覆盖状态与完成标准

状态按“未研究、已定位、已解释、已实践、已验证”记录，同时保存适用深度。只要求定位的模块可以在定位层完成，但不能计入机制实践率。

定位率的分母是基线范围内的模块；机制讲解率的分母是审核后的机制清单；实验验证率的分母是要求实验的条目。每次报告同时列出分子、分母、排除项和未解决问题，避免笼统宣称百分之百掌握。

### 7.4 从流程决定精读范围

至少研究启动、输入认领、请求组装、模型流、工具执行、取消、投影、重启恢复、多 Agent 协作与客户端更新。每条流程都检查控制、数据和资源生命周期。

核心包是研究起点。流程进入重试、上下文、作用域、投影或激活等其他实现时，继续追踪必要代码，不以固定包数或行数截断解释。

### 7.5 事实与设计分析

源码和测试确认行为；维护中的文档说明公开使用方式；设计记录提供取舍依据。缺少原始记录的设计动机写为基于实现的分析，不替作者编造意图。

模型请求的相关输入需要能从会话记录及其解释规则重建。业务数据库、文件和外部服务各有自己的权威来源；执行日志不能自动证明外部操作成功。

## 八、实验设计与验证

### 8.1 分别定义模型凭据、外网与可重复结果

核心实验不使用真实模型凭据，可以使用明确标注的测试凭据。完成依赖准备后，只有通过阻断外网验证的实验才标记为可离线运行。安装、浏览器下载和构建准备的网络需求另列。

可重复验证针对具体断言，而不要求所有时间戳和临时路径逐字相同。并发、时钟、端口与文件影响需要受控；不能为了通过而抹去有意义的状态差异。

### 8.2 三种实验方式

| 方式 | 用来证明什么 | 不能代替什么 |
| --- | --- | --- |
| 模拟模型与故障服务 | 给定响应和协议故障下的行为 | 当前真实模型与业务服务的集成效果 |
| 已录制会话回放 | 已有输入场景的记录与显示符合预期 | 未录制的新业务行为与任意交互 |
| 真实集成 | 当前外部系统、模型或平台下的功能 | 所有故障组合的可控验证 |

模拟服务按请求到达顺序消费脚本。并发会话需要独立实例或受控顺序；固定随机种子不能单独保证每个会话获得相同故障。

### 8.3 每个实验的最小说明

每项实验记录 ID、目标、知识依赖、基线、平台、环境准备、输入、步骤、预期结果、断言、失败场景、清理与证据位置。临时 Harness home、工作目录、端口、环境变量和进程归属必须明确。

运行步骤分别说明 PowerShell 与适用的其他 shell。涉及源码、构建产物、`start:web` 与 `dev:web` 时，写清构建与更新条件；正文只发布在目标环境运行验证过的命令。

### 8.4 基础实验编排

| 实验组 | 内容 | 所属学习阶段 |
| --- | --- | --- |
| L01–L03 | 黑盒观察、基础练习、第一次插件加载与卸载 | 第一、二篇 |
| L04–L05 | profile 组合、最小会话与请求观察 | 第三、四篇 |
| L06–L07 | 工具循环、教学最小实现与取消 | 第四篇、综合项目一 |
| L08–L09 | 投影、持久化与受控重启恢复 | 第五篇 |
| L10–L11 | 能力替换、确认写入与结果核查 | 第六篇 |
| L12 | 子 Agent 等待、中断与父级收敛 | 第七篇、综合项目二 |
| L13–L14 | 外部程序驱动、业务卡片与人工反馈 | 第八、九篇 |
| L15–L16 | 干净环境交付、迁移案例 | 第十篇、综合项目三 |

实验组可以包含多个小练习。正式清单需要逐项拆分断言；表格本身不表示设施已经存在。

### 8.5 验证外部结果并精确命名恢复

业务修改后重新读取业务状态，文件操作后检查文件，卸载后检查注册项与进程，界面交互后检查实际显示和可访问行为。Agent 自述只属于输出的一部分。

请求重试、会话重新附着、进程重启、格式迁移和业务补偿分别编写实验。它们的前置状态、保证与失败后处理方式不同，不能以一句“恢复成功”合并验收。

### 8.6 设施与证据的当前状态

仓库提供模拟 LLM 服务、会话回放及相关脚本入口。本轮只沿用前次评审的有限证据：文档与部分实现已经检查，模拟服务帮助命令曾成功退出；没有据此宣称教材实验已全部通过。

每项正式实验保存基线、平台、命令、断言、输出或报告、退出状态、清理结果和未验证范围。真实模型、外部业务与平台专项单独标注条件；基础 CI 不默认承担所有集成实验。

## 十、审校与读者验收

### 10.1 每章先检验理解，再检验迁移

读者先复述机制，再运行实验，然后独立修改一个条件，最后处理一个不同于正文例子的需求。迁移练习需要说明选择和验证方法，避免只替换名称即可通过。

对兴趣的观察包括读者是否愿意继续、在哪一段停下来以及原因。对理解的观察包括陌生术语、回翻位置、解释能力和求助次数。不能为了让反馈好看而替试读者完成步骤。

### 10.2 技术与编辑两轮审校

技术审校检查行为、类型、资源、数据、权限、失败与验证；编辑审校检查读者起点、段落连接、术语、例子、节奏和重复。需要删减时，先保留关键保证与失败条件，再调整表达。

源码引用、文档链接、代码块、实验清单和术语可以自动检查。符号存在不等于使用正确，代码编译不等于运行符合业务，自动检查之后仍需对应的实验与人工审核。

### 10.3 章节完成条件

- 本章问题已经回答，读者能明确说出学会了什么。
- 前置知识有入口，代码与数据有坐标，新增术语有解释。
- 操作说明在声明的平台与基线运行验证。
- 相关失败、取消或恢复有明确结果与处理责任。
- 设计动机有依据，推断有标记，外部结果经过核查。
- 试读状态如实记录，已知问题不会被“已完成”掩盖。

## 十一、资料组织与版本维护

建议将正文、参考、实验和验证记录分开组织，并通过稳定 ID 相互链接。先在当前 `artifacts/` 中维护规划；新建独立教材仓库、迁移文件、公开发布或改变源码仓库结构另行确定，不由本规划自动触发。

每次升级书稿先比较代码与依赖变化，再定位受影响章节、实验、模块和扩展点。旧书稿保留适用提交，新版说明验证范围；关键机制变化时及时更新，不只等待固定季度。

仓库统计需要保存统计脚本、范围、排除项、提交与输出。v2 的历史包数、行数与测试数量在本轮没有重新全量核实，因此不作为新版覆盖率分母或排期依据。

正式进入仓库文档体系时遵循所属目录的文档规范、语言配对与验证要求。书中的讲解链接权威资料，不复制维护完整 API 清单；独立出版保留来源与第三方许可说明。

## 十二、首批交付清单

第一批交付包括详细目录与学习依赖图、模块及机制及扩展点清单骨架、两章样章、各自实验与验证记录、试读反馈表。

样章一选择“一句请求发出去以后”，检验零基础读者是否能从观察建立整体认识。样章二选择“第一个业务工具”，提供所需基础补课入口和准备好的环境，检验问题、源码、修改与结果能否连起来。

样章二提前试写不代表学生阅读时可以跳过基础。样章验证后再调整正文顺序、章节规模、语言细节与预算，形成可持续执行的写作计划。
